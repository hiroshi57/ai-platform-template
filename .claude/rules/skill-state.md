# 実行状態ルール（SKILL.state 方式）

> **適用対象**: 手順の決まった長い作業を回す Lead / Worker、および Worker の再試行ループ
> **起源**: 提案 `harness-proposals/2026-09-28-skill-state-runtime.md`（提案 B・C・D）／根拠 arXiv:2608.26263
> **承認**: 2026-09-28 人間承認済み（B・C・D）

## 背景

会話履歴を追記し続ける実行方式では、手順が長くなるほどトークン消費が O(T²) で増え、古い観測に
引きずられて誤る。論文では、各ステップの入力を「手順書 P・構造化した状態 σ・最新の観測 O」に限り、
推論は状態更新を出した時点で捨てる方式で、総トークンを最大 16 分の 1 にし、正解率も維持または向上した。
ただし、効果の大きさはモデルや環境で差がある。特に小型モデルでは、状態 JSON を正しく書けないことが
主なボトルネックになる。

## ルール（MUST）

1. **再試行に渡すのは状態であって、履歴ではない。** Worker の再試行・修復ループでは、過去の推論や
   観測の全文を次の試行に渡さない。次の試行に必要な過去は、状態の `tested_hypotheses`
   （何を試したか・どのチェックで落ちたか）に構造化して渡す。同じ修復を繰り返さないためである。
2. **状態の更新はパッチで行い、検証と適用はランタイムが担う。** モデルに状態を丸ごと書き直させない。
   - パッチに書かれていないキーは残す。削除は `null` を明示したときだけ受け付ける。
   - 追記型の配列（`completed`・`tested_hypotheses` など）は追加分だけを受け付け、既存要素を消させない。
   - 型の違反・未知のキー・変更不可のキーを含むパッチは、**一部だけ適用することはせず、状態を一切
     変えずに差し戻す**（rollback）。そのうえで再試行させる。
   - 実装例: `agent-harness/src/state-patch.mjs`（`applyPatch` / `parseStepOutput`）
3. **スキーマは領域ごとに1回だけ定義する。** タスクごとに作り直さない（例: `WORKER_STATE_SCHEMA`）。
4. **小型モデルを状態の書き手にするときは出力を縛る。** 状態パッチを小型モデルに書かせる場合は、
   JSON Schema による出力制約（constrained decoding / structured output）を併用する。
5. **状態に秘密を書かない。** 状態は毎ステップ必ずコンテキストに入るので、秘密が入ると全ステップに
   持ち越される（`.claude/rules/secret-isolation.md` ルール1・6）。値ではなく、参照先（パスやキー名）だけを持たせる。

## 他ルールとの関係（MUST）

6. **捨てるのは「次のプロンプトに入れる推論」だけで、保存するログは捨てない。** 推論をプロンプトから
   外しても、`harness-logs/` への生ログの逐語保存（`memory-curation.md` ルール4・CLAUDE.md §7）は
   そのまま続ける。保存前には、`secret-isolation.md` ルール6に従って秘密をマスクする。
7. **履歴そのものが目的のタスクには使わない。** 次の場合は本方式を使わず、生ログや履歴を参照させる。
   - harness-retro（生ログを読ませること自体が目的。`.claude/rules/harness-retro.md`）
   - 監査・原因追跡・過去の行動の説明
   - スキーマが事前に決められない探索的なタスク
8. **後から重要になる観測に注意する。** 観測の時点では重要と分からず、状態に書き込まれなかった情報は
   失われる（論文 §7 の限界2）。この取りこぼしが疑われる失敗が出たら、スキーマに項目を足す。
   履歴を渡す方式には戻さない。

## セルフチェック（コミット前）

- 再試行ループのプロンプトに、前回までの推論や観測の全文が入っていないか。
- 状態の更新が、パッチの検証・適用を通らずに直接代入になっていないか。
- 状態・ログに秘密らしき文字列を書いていないか（`secret-isolation.md` のセルフチェック grep）。
