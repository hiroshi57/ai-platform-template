## 要旨（Abstract）

企業がレガシーシステムを近代化する（例: モノリシックな Java アーキテクチャを Python マイクロサービスへ）際、大規模言語モデル（LLM）は自動コード翻訳において不可欠な存在となっている。しかし従来のベクトルベースの検索拡張生成（Standard RAG）は**トポロジー的な関係の扱いに苦労する**。孤立したテキスト片を取ってくるため、しばしば継承チェーンを分断し、高いコンパイル失敗率を招く。

本論文は Standard RAG と、新規手法である **Hierarchical Context-Resident Graph（HCRG／階層的コンテキスト常駐グラフ）** の比較分析を提示する。我々のパイプラインは、多言語対応の抽象構文木（AST）抽出に **tree-sitter** を用い、アーキテクチャ上のエッジを **Google Cloud Spanner のプロパティグラフ**にマッピングし、この構造を **Gemini（Vertex AI 上）の Context Cache** にシリアライズして、トポロジーに沿った **親優先（parent-first）のコード翻訳**を可能にする。

評価を、素朴なテキスト重複からソフトウェア工学（SE）上の実用性を測る**独自の7指標フレームワーク**へと移すことで、`spring-petclinic-genai` リポジトリでの実証評価は有意な構造的改善を示した。**Graph RAG は依存関係の欠落を決定的に緩和し、API ハルシネーション率を 56.4% から 16.2% へ低下させた。** さらに **Dependency Resolution Quality（DRQ）を 34.8% から 65.9% へ改善**し、**Parent-Child Consistency（PCC）を 26.7% から 45.5% へ向上**させた。興味深いことに、従来の字句的指標はこの乖離を捉えられない。**両手法とも同一の平均 CodeBLEU スコア 91% を達成**し、構文的にはもっともらしいが壊れたコードの背後に、Standard RAG の構造的失敗を実質的に覆い隠していた。

ただし、結果は **Graph RAG が全次元で厳密に優位なわけではない**ことを示す。LLM に密でグローバルな構造コンテキストを与えると新たな脆弱性が生まれる。**Graph RAG は Cyclomatic Complexity Consistency（循環的複雑度の一貫性）で深刻な劣化を被り（Standard RAG の 71.6% から 46.7% へ低下）**、これは LLM による**防御的な過剰設計（defensive over-engineering）**が原因である。加えて、プロンプトの注意希釈（attention dilution）により **Docstring Preservation もわずかに低下した（67.0% から 61.0% へ）**。

最終的に本研究は、Graph RAG がコード複雑度の増加と引き換えに API ハルシネーションを決定的に削減する一方で、**自動的な企業コードベース近代化にとって、はるかに実用的でアーキテクチャ的に健全な道筋**を提供することを実証する。

## 1. 導入（Introduction）

モノリシックでレガシーなコードベースをモダンなマイクロサービスへ移行するには、行単位の構文翻訳をはるかに超えるもの——深くネストしたアーキテクチャ的意図の理解——が求められる。企業ソフトウェアは高度に結合しており、単一の業務処理が複数のファイル・インターフェース・基底クラスにまたがる。LLM は局所的なコード生成には優れるが、ベクトル検索拡張生成（Standard RAG）を用いた標準的な「コードベースとチャットする」パラダイムは、テキストのチャンク化プロセスがもたらす意味的境界によって本質的に制約される。

LLM が子クラスを翻訳しようとするとき、意味的検索は——高い字句的重複を共有しない限り——継承元の親クラスや離れたユーティリティインターフェースを取ってこられないことが多い。この**構造的な盲目性**がトポロジー関係を分断し、高いコンパイル失敗率・import 欠落・深刻な API ハルシネーションを招く。

グラフベースの検索拡張生成（Graph RAG）は、ソフトウェアを浮遊するテキスト埋め込みの集まりではなく**決定論的なネットワーク**としてモデル化することで、この限界に対処する。近年の文献は、AST 由来の知識グラフが純粋な意味的検索に対して優れた説明可能性と追跡可能性を提供すると強調している [1, 2, 3]。このパラダイムを前進させるため、本論文は新規手法である **HCRG（Hierarchical Context-Resident Graph）** に支えられた「コンテキスト対応移行パイプライン」の設計と評価を提示する。

**tree-sitter** を利用して、我々は多言語対応の抽象構文木（AST）を決定論的に抽出し、そのアーキテクチャ的依存関係（例: `INHERITS`, `CALLS`, `IMPORTS`）を Google Cloud Spanner のプロパティグラフにマッピングする。この構造を単に「クエリされるデータ」として扱うのではなく、HCRG パイプラインはリポジトリの「アーキテクチャ骨格（Architecture Skeleton）」をシリアライズし、Vertex AI Context Caching を通じて LLM の作業メモリ内にキャッシュする。このグローバルに認識された状態により、パイプラインは**トポロジカルソートされた移行**——子クラスより先に親クラスを翻訳する——を編成でき、LLM は孤立した意味的スニペットに頼るのではなく、**新たに生成された Python の親コードによって文脈的に接地（grounded）**される。

この AST 由来 Graph RAG パイプラインの有効性を Standard RAG ベースラインと厳密に比較評価するため、我々は高度に結合した `spring-petclinic-genai` リポジトリで Java→Python の自動移行を実施する。重要なのは、**なぜ従来の LLM 評価指標が Graph RAG のアーキテクチャ的優位性を捉えられないのか**を実証する点である。字句的な N-gram 重複に主に依拠するため、Standard RAG と Graph RAG は我々の実験で**同一の平均 CodeBLEU スコア 91%** を達成し、根底の構造的失敗を覆い隠す「偽の等価性」を作り出した。

生成コードの真の実用性を明らかにするため、我々は7つのソフトウェア工学（SE）指標からなる詳細な AST ベース評価フレームワークを導入する: **Code Migration Quality（CMQ）、Parent-Child Consistency（PCC）、Type Hint Completion（THC）、Linter Status（StaQ）、Dependency Resolution Quality（DRQ）、Cyclomatic Complexity Consistency（CCC）、Docstring Preservation（DP）**。

この厳密なプログラム的評価を通じて、我々は次を明らかにする。Standard RAG は構文的にもっともらしいコードを生成するが、**その出力の半数超で API と依存関係をハルシネーション（幻覚）している（56.4% のハルシネーション率）**。対照的に Graph RAG は、グローバルなクロスファイル解決の照会を活用して真のハルシネーション率を **16.2%** へ低下させ、同時に Dependency Resolution Quality を（34.8%→65.9%）、Parent-Child Consistency を（26.7%→45.5%）劇的に改善する。

ただし本研究は、Graph RAG が一様に優れていると結論づけるものではない。リポジトリ構造の包括的な「神の視点（god's-eye view）」を LLM に与えることで、Graph RAG は**防御的な過剰設計**を誘発し、循環的複雑度の肥大化と、Docstring Preservation のような二次タスクへのプロンプト注意のわずかな劣化をもたらす。本論文は HCRG パイプラインのアーキテクチャを詳述し、これらの経験的トレードオフを解剖し、企業コード近代化で決定論的グラフを活用するための設計図を提供する。

なお重要な点として、本研究は実験参照実装に Google Cloud Spanner と Gemini 2.5 Pro（Vertex AI）を活用しているが、根底にある **HCRG 手法は本質的にプラットフォーム非依存**である。中核となるアーキテクチャ原則——決定論的な AST 取り込み、グラフベースのトポロジカルソート、コンテキスト常駐キャッシング——は、標準的なプロパティグラフデータベースと同等の生成 AI サービスであれば、オンプレミスでも他のクラウド環境でも等しく適用・展開可能である。

## 2. 用語集（Glossary of Terms）

本比較分析全体を通じた明確さを担保するため、評価パイプラインで参照される中核的な機構・手法・指標を定義する。

**抽象構文木（AST）**
ソースコードの構文構造を表す、高度に構造化された階層的な木。素朴な正規表現マッチングと異なり、AST は構造的境界（クラス、関数定義、引数）を決定論的に抽出でき、元コードの意味的意図を正確に捉えられる。我々の取り込みパイプラインでは、Java・Python・Go にまたがる堅牢な多言語 AST 解析を行うために **tree-sitter** を利用する。

**Standard RAG（ベクトル検索）**
テキストを恣意的なチャンク（例: 再帰的文字スプリッタを使用）に分割し、それらを数学的な高次元ベクトル空間に埋め込む検索フレームワーク。検索はユーザーのプロンプトに対するコサイン類似度に完全に依拠する。深くネストした子クラスが、継承する重要なインターフェースと字句的にも意味的にもゼロの類似度しか持たないことがあり得るため——それによりトポロジー関係を分断するため——コード移行にはしばしば不十分である。

**Graph RAG**
テキストとトポロジー関係を決定論的なグラフデータベースにマッピングする高度な RAG フレームワーク。厳密なエンティティ関係に基づく精密なマルチホップのコンテキスト検索（例: グラフエッジを明示的に辿って、対象クラス・それが実装する特定インターフェース・それが呼ぶリモートメソッドを取得）を可能にし、存在しない API のハルシネーションを劇的に削減する。

**Hierarchical Context-Resident Graph（HCRG）**
本論文が導入する新規アーキテクチャ手法。LLM を単なる推論エンジン、グラフを単なる孤立ストレージとして扱うのではなく、HCRG はリポジトリの最上位構造を Vertex AI Context Caching を通じて LLM のアクティブな作業メモリにシリアライズする。これにより、アーキテクチャ推論のためのゼロレイテンシな走査を可能にしつつ、深い AST チェーンについては動的にグラフデータベースへフォールバックする。

**Architecture Skeleton（アーキテクチャ骨格）**
リポジトリ全体の「ホットなアーキテクチャ」（クラス、親階層、メソッドシグネチャを含む）を凝縮・シリアライズした JSON 表現。この骨格はグラフクエリによって構築され、生成に先立って LLM に低レイテンシな「神の視点」を提供するために Context Cache へプッシュされる。

**有向非巡回グラフ（DAG）**
有向閉路を持たない数学的トポロジー構造。我々のパイプラインでは、コードベースの継承ツリーを DAG に変換し、ファイルを移行すべき正確な時系列順序を規定する（例: `BaseEntity` を `Person` より先に、`Person` を `Vet` より先に翻訳することを保証）。これにより、新たに生成された Python の親コードが、子クラス生成時の厳密な文脈的接地として機能する。

**Spanner プロパティグラフ**
Google Cloud Spanner のグローバル分散データベースエンジン。本アーキテクチャでは、リレーショナルな表データとグラフデータをネイティブに統合するために利用する。論理的な AST ノード（例: `CodeFiles`, `CodeStructures`, `Callables`）、ベクトル検索用のネイティブな `ARRAY<FLOAT64>` 埋め込み、エッジ（例: `INHERITS`, `CALLS`, `IMPORTS`）を格納し、すべて ISO 標準のグラフクエリ言語（GQL）で照会される。

**ソフトウェア工学（SE）実用性指標**
CodeBLEU のような汎用的字句指標に取って代わるべく設計された、我々独自のプログラム的評価フレームワーク。移行の実用性に合わせた7つの決定論的指標からなる: Code Migration Quality（CMQ）、Parent-Child Consistency（PCC）、Type Hint Completion（THC）、Linter Status（StaQ）、Dependency Resolution Quality（DRQ）、Cyclomatic Complexity Consistency（CCC）、Docstring Preservation（DP）。

## 3. アーキテクチャのパラダイムと図

### 3.1 ベースライン手法: Standard RAG（ベクトル検索）

比較のベースラインを確立するため、我々はコードベースを平坦なテキストコーパスとして扱い、トポロジー関係よりも意味的類似度を優先する従来型の検索拡張生成（Standard RAG）パイプラインを実装した。対象ソースファイル（`.java` と `.proto`）は、素朴な再帰的文字スプリッタで処理される。これらの孤立したチャンクは埋め込まれ、ベクトルデータベースにインデックスされる。

このアプローチの根本的な限界は、**意味的類似度が構造的関連性に等しいと仮定している**点にある。字句的重複に依拠するため、パイプラインは翻訳に必要な実際の親クラスや離れたインターフェースではなく、並列の兄弟クラスをしばしば取ってくる。これが、標準的な LLM コード生成で観測される高い API ハルシネーション率と貧弱な Parent-Child Consistency（PCC）の主要な触媒として働く。

> **図1（Standard RAG のフロー）**: レガシー Java コード（GitHub リポジトリ）→〔ナイーブ分割〕→ テキストチャンク → Vertex AI 埋め込み → ベクトルデータベース。一方、ユーザークエリ「リポジトリを移行せよ」→ クエリ埋め込み → K近傍探索 → 孤立したコンテキストチャンク → Gemini 2.5 Pro プロンプト → 生成 Python コード。
>
> **限界**: コンテキスト欠落（親クラスの欠落）、隠れた依存（離れたファイルに格納された暗黙の trait や設定）、シングルホップ推論の境界。

### 3.2 Graph RAG アーキテクチャ（HCRG）

Graph RAG は、ソフトウェアを平坦なテキストコーパスではなく決定論的なネットワークとしてモデル化することで、コードベース検索を根本的に変える。AST 解析に **tree-sitter** を利用し、我々の HCRG パイプラインはアーキテクチャ上のエッジ（`INHERITS`, `CALLS`）を Spanner プロパティグラフにマッピングし、この構造骨格を LLM の作業メモリ内にキャッシュする。

このグローバルな認識により、トポロジカルな編成が可能になり、循環依存を解決して親クラスが依存する子より先に翻訳されることを保証する。事前翻訳済みの親階層をプロンプトに明示的に注入することで、LLM は意味的推測ではなく正確な構造的依存によって文脈的に接地される。この決定論的機構は、アーキテクチャ劣化の根本原因に直接対処し、複雑なレガシー近代化中に欠落 API を幻覚したり継承構造を推測したりするモデルの能力を劇的に制限する。

> **図2（Graph RAG / HCRG のフロー）**: レガシー Java コード → Tree-Sitter AST → グラフ抽出（ノード & エッジ）→ Spanner プロパティグラフ → 移行オーケストレータ → トポロジカルソート（DAG）→ 対象クラスのサブグラフ。〔GQL 走査〕により親サブグラフを取得し、Gemini 2.5 Pro + Context Cache → Gemini 2.5 Pro プロンプト → アーキテクチャ的に一貫した Python コード。

## 4. パイプラインの革新と実験設定

再現性を担保し移行中のグラフの有用性を最大化するため、我々は両パラダイムにわたって実験設定を標準化した [5]。

### 4.1 パイプライン最適化

- **トポロジカル移行キュー（HCRG）**: ファイルを恣意的またはアルファベット順に翻訳するのではなく、Graph RAG オーケストレータは Spanner プロパティグラフを GQL で照会して `INHERITS` と `CALLS` のエッジを抽出し、有向非巡回グラフ（DAG）を構築する。循環依存を動的に解決し、基底/親クラスを**必ず先に**翻訳することを義務づける。新たに生成された Python の親コードは、子クラス生成時に LLM プロンプトへ直接注入される。この厳密な文脈的接地により、正確な `super().__init__()` マッピング、正しいメソッドオーバーライドが保証され、継承属性のハルシネーションが劇的に削減される。

- **Context Caching（「アーキテクチャ骨格」）**: リポジトリの巨大な構造表現を繰り返し LLM に渡すことによるトークン制限とレイテンシのオーバーヘッドを回避するため、Vertex AI Context Caching API を利用する。パイプラインは Spanner を照会し、抽出された全クラス・親子関係・メソッドシグネチャを含むグローバル JSON「骨格」を構築する。このグローバルグラフ骨格を **1時間の TTL（Time-To-Live）** でキャッシュすることで、限界入力トークンコストとレイテンシを劇的に削減し、`gemini-2.5-pro` モデルにあらゆる翻訳ステップでシステム全体のアーキテクチャの永続的・低レイテンシな「神の視点」を提供する。

- **統合セマンティック・フォールバック（ベクトル検索）**: トポロジカルなエッジが明示的依存を扱う一方、パイプラインは Spanner ベクトル検索によるコサイン距離を同時に利用して暗黙的関係を捕捉する。抽出された AST ノードは Vertex AI で埋め込まれ、Spanner 内でグラフノードと並べてネイティブな `ARRAY<FLOAT64>` 型として格納される。このハイブリッドアプローチにより、パイプラインは意味的に関連するコード構造（例: 疎結合なユーティリティ関数や非構造ドキュメント）を取得し、厳密なトポロジーコンテキストを補完できる。

- **自動リポジトリ再構築**: パイプラインは孤立したコードスニペット生成を超えて、対象リポジトリをコンパイル可能な状態へ物理的に再構築する。Java の深くネストしたディレクトリパスと `PascalCase` のファイル慣習を、慣用的で平坦な Python の `snake_case.py` モジュールへ自動変換する。さらに、有効な Python パッケージを作るために必要な `__init__.py` ファイルを自動生成し、元の非コード資産（YAML, XML, Proto）を保存し、コード翻訳と機能的デプロイのギャップを実質的に橋渡しする。

### 4.2 実験設定パラメータ

2手法の厳密で客観的な比較を提供するため、`spring-petclinic-genai` リポジトリの移行にわたってベンチマークパラメータとインフラ構成を厳密に定義した。

- **Standard RAG の取り込み**: 対象ソースファイル（`.java` と `.proto` 資産を含む）を再帰的文字テキストスプリッタで処理。業界標準の慣行を模倣するため、チャンクサイズを **800文字**、末尾のコンテキスト境界を保持するオーバーラップを **150文字**に設定。埋め込みは Vertex AI の `text-embedding-004` モデルで生成。
- **Standard RAG の検索**: コサイン距離を利用した K近傍（KNN）ベクトル検索を実行するよう構成し、Spanner データベースからプロンプト注入用に**上位 k=5** の最も意味的に類似したテキストチャンクを取得。
- **Graph RAG の取り込み（HCRG）**: 平坦なチャンク化と異なり、ソースコードは tree-sitter を利用して抽象構文木（AST）へ決定論的に解析される。論理ノード（例: クラス、メソッド）とトポロジカルエッジ（例: `INHERITS`, `CALLS`, `IMPORTS`）が Google Cloud Spanner プロパティグラフへ明示的にマッピングされる。
- **Graph RAG の検索とキャッシング**: 走査深さの上限を **3ホップ**（例: 対象クラス→実装インターフェース→親基底クラス）に構成し、GQL 経由で実行。LLM のコンテキスト制限を最適化しレイテンシを削減するため、リポジトリのグローバルアーキテクチャ骨格を Vertex AI Context Caching（**TTL 1時間**）でモデルの作業メモリに永続化。
- **生成モデル**: 両パイプラインとも Google の Gemini モデル（具体的には `gemini-2.5-pro`）を中核翻訳エンジンとして利用。生成温度は静的値（**T=0**）に明示的に制約し、創造的な逸脱とロジックのハルシネーションを最小化しつつ、高度に予測可能で決定論的なコード生成を保証。

## 5. 評価ロジックの方法論と強化されたコンテキスト

企業コードベースの自動移行を評価することには、独特の難しさがある: **構文的な類似は、アーキテクチャ的な実用性に等しくない**。CodeBLEU のような従来の機械翻訳指標は、字句的 N-gram 重複に大きく依拠しており、パラダイム横断的な近代化タスク（例: Java の堅いオブジェクト指向構造から Python の動的パラダイムへの移行）には本質的に不向きである。我々の対照実験が示すように、LLM は Java 特有のイディオムを強引に持ち越したり、存在しない API を Python モジュールへ幻覚したりして、人工的に高い N-gram 重複を生み出しうる——我々のベースラインと実験パイプラインは同一の 91% CodeBLEU スコアを達成した——一方で、実行可能なコードの生成には完全に失敗しうる。

これら意味的重複指標の「覆い隠し効果」を克服するため、我々は真のソフトウェア工学（SE）実用性を定量化するよう設計された決定論的でプログラム的な評価スイートを構築した。トポロジー検証には Python の `ast`（抽象構文木）モジュールを、構文検証には `pyflakes` 静的解析エンジンを活用することで、このフレームワークは評価パラダイムをテキスト予測から**構造的忠実性**へと移す。我々は、集約された **Migration Quality** スコアを軸とした包括的な7指標フレームワークを導入し、依存解決・型ヒント充足・親子継承一貫性を含む、近代化の重要な次元を厳密に評価する。

### 5.1 Migration Quality（MQ）の再定義

Migration Quality（MQ）は、真の機能的実用性を表すよう設計された独自の加重合成スコアである。クロスファイルのロジックのマッピングに失敗するモデルを重く罰する。厳密には次のように計算される:

- **依存解決（重み 40%）**: モデルが import と API 呼び出しをうまく翻訳できたかを評価。
- **継承の正確さ（重み 30%）**: OOP の構造階層が正確に維持されているかを評価。
- **型の完全性（重み 20%）**: モダンな Python 型ヒントの存在を評価。
- **構文の正しさ（重み 10%）**: 構文リンティングによる基本的なスクリプトのコンパイル可能性を評価。

### 5.2 詳説: AST 評価指標の抽出

我々の評価スクリプトは、生成された Python コードベースを動的に解析し、MQ スコアを構成する正確なサブ指標を算出する:

- **依存・API 解決（DRQ）**: 生成 Python コードを AST 経由で解析し `ast.Import` と `ast.ImportFrom` ノードを抽出。これらの import を `sys.stdlib_module_names` と許容される内部ホワイトリスト（例: `config`, `src`, `spanner`, `vertexai`）と照合。最後に `importlib.util.find_spec` で動的な利用可能性を確認する。幻覚された、または解決不能なライブラリはスコアを下げる。

- **Parent-Child Consistency（PCC）**: オブジェクト指向 Java を Python へ翻訳するには、綿密な継承マッピングが必要。スクリプトは元 Java から真の継承意図を正規表現で抽出する（`extends` と `implements` を識別、ジェネリクスは意図的に無視）。次に生成 Python コードを解析し、`ast.ClassDef` 内の `node.bases` を特に検査する。Python クラスが翻訳された親を継承し損ねた場合（または幻の親を発明した場合）、不一致としてフラグする。

- **Type Hint Completion（THC）**: AST を走査して全 `FunctionDef` と `AsyncFunctionDef` ノードを取得。完全に型付けされた引数の比率を計算する（`args`, `kwonlyargs`, `vararg`, `kwarg` を検査、Python で型ヒントを要さない `self` と `cls` は明示的に無視）。厳密なシグネチャ強制のため `node.returns`（戻り値型）の存在も検証する。

- **静的解析／Linter スコア（StaQ）**: `pyflakes` エンジンを用いて、一時ファイルに格納した生成 Python コードに対し構文・lint ルールチェックを直接実行。局所的な構文エラーや未使用/未定義変数1件につき **10点減点**する。

- **循環的複雑度の一貫性（CCC）**: `lizard` ライブラリを用いて、元 Java（CC_Java）と生成 Python（CC_Python）の循環的複雑度を計算。絶対偏差に基づく百分率スコアを算出する。自然な言語シフト（例: Python のリスト内包表記は Java のネストループより自然に単純）を考慮し、**偏差 2 または 10% までは「一貫」**とみなす許容を与える。

### 5.3 ハルシネーションの「Global Lookup（グローバル照会）」機構

従来のファイル単位のハルシネーションチェックは、Graph RAG にとって意味的境界により本質的に制約される。Graph RAG は深い依存を能動的に解決するため、LLM は別々のモジュールで定義された内部・カスタムのリポジトリメソッドへの呼び出しを正しく生成する。素朴なファイル単位の評価スクリプトは、これら正当なクロスファイル呼び出しを、単にメソッド定義が翻訳中の局所ファイルに存在しないという理由だけで「ハルシネーション」とフラグしてしまう。

これを是正するため、我々は **Global Lookup（Universe）制約**を実装した。`ast.Call` ノードは、以下の**いずれにも存在しない**場合にのみハルシネーションと判定される:

1. ローカルの翻訳ファイル（Local Golden）
2. Python builtins（例: `print`, `len`）
3. 一般的なコレクションメソッドのホワイトリスト（例: `append`, `keys`, `split`）
4. Spanner コードベース全体を表す **Global Symbols Table**

## 6. 実証結果と分析

我々は `spring-petclinic-genai` リポジトリの Java→Python 移行をベンチマークした。高度なカスタムパーサを利用し、コア Java ファイルと生成 Python 相当物の厳密な 1対1 マッピングを保証した。データが示すように、Graph RAG は構造的完全性を劇的に改善する——Dependency/API Resolution を 31.1%、Parent-Child Consistency を 18.8% 押し上げる——一方で、ハルシネーション率を 16.2% まで削り落とすことに成功した。

| コア指標 | Standard RAG | Graph RAG | Δ（差分）|
|---|---|---|---|

| 平均 ハルシネーション率 | 56.4% | 16.2% | -40.2% |

### 6.1 構造的完全性とオブジェクト指向マッピング

Graph RAG は、機能的完全性とコンパイル可能性を決定づける構造的完全性の指標で、Standard RAG を有意に上回る。データが示すように、**Dependency & API Resolution Quality（DRQ）は 31.1% 改善**（34.8%→65.9%）し、**Type Hint Completion（THC）は 29.5% 向上**（51.4%→80.9%）した。これらの利得は、コードベースの決定論的な骨格——具体的には外部依存の正確な戻り値型とシグネチャ——を LLM に明示的に提供することが、OOP の正確性を劇的に改善することを証明している。Standard RAG は、その特定情報が素朴なベクトル類似度で取得される直近隣接テキストチャンクにめったに存在しないため、正しい基底クラスや適切な型ヒントの特定にしばしば失敗する。

さらに、HCRG パイプラインのトポロジカルソート機構は **Parent-Child Consistency（PCC）を 18.8% 改善**（ベースライン 26.7% に対し 45.5%）した。親クラスを先に翻訳し、その正確な Python 実装を子クラスのプロンプトへ注入することで、Graph RAG は正しい継承構造と `super().__init__()` マッピングを強制する。

結果として、Graph RAG の真の **API ハルシネーション率は極めて正確な 16.2% まで急落**した。対照的に Standard RAG は、基本的なテキスト翻訳を行うため、複雑なクロスファイル依存の実装詳細を LLM に盲目的に推測・幻覚させることを強い、このテストに壊滅的に失敗した（56.4% のハルシネーション率）。

### 6.2 字句重複バイアスと文脈的トレードオフの分析

興味深いことに、従来の機械翻訳指標はこの構造的品質の大きな乖離を完全に捉えられなかった。Standard RAG と Graph RAG は **CodeBLEU 指標でほぼ同等**（90.6% 対 91.1%）を達成した。これは偽の等価性を作り出し、**CodeBLEU が局所的な文字列重複に強くバイアスし、深刻に壊れた API 契約や幻覚された import をモジュールに対して罰することができない**ことを実証している。Standard RAG の「素朴な翻訳」的振る舞いは、一見正しく見える極めて読みやすい Python コードを生むが、実行時に失敗する。

しかし評価は、Graph RAG 手法が導入する重大なトレードオフも明らかにした。Context Cache 経由でリポジトリの巨大な「神の視点」を LLM に与えることで、Graph RAG は **Cyclomatic Complexity Consistency（CCC）で深刻な劣化**を被り、ベースラインに対し **24.9% 低下**（46.7% 対 71.6%）した。実際のアーキテクチャコンテキストを持つことが、LLM に依存グラフ上で見つけた遠いエッジケースに対して能動的に**過剰設計**し防御的にコードさせ、肥大化して極めて複雑な Python メソッドを招く。

加えて、Graph RAG は **Docstring Preservation（DP）でより低いスコア**（61.0% 対 Standard RAG の 67.0%）となった。これは**プロンプト注意希釈**の直接的な症状である。LLM のコンテキストウィンドウが厳密なトポロジールール・親クラス実装・Spanner GQL スキーマで大きく飽和すると、その注意機構はアーキテクチャの健全性を優先し、元の JavaDoc コメントの移植のような二次的なシステム指示をしばしば「忘れる」。この知的で文脈重視のリファクタリングは、素朴なテキスト一致・保存スコアをわずかに下げるが、企業近代化中に機能的でコンパイル可能なコードを達成する唯一の実行可能な道筋であり続ける。

### 6.3 クラスレベルの分散分析

HCRG アーキテクチャが Standard Vector RAG を正確にどこで上回り、どこで新たな複雑さを導入するのかを理解するため、我々はファイルを Migration Quality の分散で分離し、個々の性能指標をまとめた。

## 7. 結論と今後の課題

Standard Vector RAG は汎用的なドキュメント検索や基本的な質問応答には依然として極めて効率的だが、複雑なソフトウェア工学タスクに適用すると意味的境界により本質的に制約される。ソースコードを抽象構文木（AST）に分解し、その関係エッジを高度にスケーラブルなプロパティグラフデータベース（Google Cloud Spanner）へロードすることで、HCRG 手法は企業近代化のために生成 AI が要するマルチホップのトポロジーコンテキストの再確立に成功する。

我々の包括的な実証的再評価は、CodeBLEU のような従来の、テキストにバイアスした機械翻訳指標——両パラダイムでほぼ同一の 91.1% と 90.6% を記録した——が、標準的な LLM 生成における重大なアーキテクチャ的失敗を能動的に覆い隠す偽の等価性を作り出すことを証明する。**Global Graph Lookups で検証された決定論的な Migration Quality フレームワーク**へ移行することで、我々は **Graph RAG が機能的翻訳精度で大きな飛躍を提供し、Standard RAG ベースラインの 65.5% に対して集約 83.2% を記録**することを実証する。最も注目すべきは、親優先のコンテキスト注入を強制するトポロジカルソートの実行により、真の API ハルシネーション率が壊滅的な 56.4% から 16.2% まで削り落とされ、同時に Dependency & API Resolution Quality（DRQ）が 31.1% 押し上げられた点である。

しかし本研究は、LLM にグローバルな構造認識を与えることの本質的なトレードオフも浮き彫りにする。**巨大でコンテキスト常駐なアーキテクチャ骨格をモデルに供給すると防御的な過剰設計を誘発し、LLM が遠いエッジケースを過剰に補償しようとするため Cyclomatic Complexity Consistency（CCC）が 24.9% 劣化**する。さらに、プロンプト注意希釈が Docstring Preservation（DP）で 6.0% の低下を招いた。モデルの注意機構が二次的なコメント翻訳よりも厳密な構造遵守を優先したためである。

今後の研究は、動的な **Hybrid RAG** アーキテクチャの開発によってこれらトレードオフを緩和することに注力する。コア OOP ロジックには決定論的な Graph RAG を、非構造ドキュメントには標準的な Vector RAG を、知的に編成して振り分けることで、理論的にはアーキテクチャの完全性と元のコードベースの循環的単純性の双方を保てる。加えて、今後の反復では、リフレクション・複雑なジェネリック型消去・動的に注入されるフレームワーク依存を解釈するよう AST パーサをスケールさせることに注力する。最終的に、静的な AST Spanner グラフを動的な実行時トレースで豊かにすることで、完全に自律的で検証可能なレガシーコードベース近代化への最後のギャップを橋渡しすることを目指す。
