## 概要

コーディングエージェントは意外に単純で、「モデル＋少数のツールを回す while ループ」にすぎない。モデル以外の部分ではほとんど革新がなかった。本書は TypeSafe の意思決定モデル **Jev**（構造化された状態を受け取り、選択・スコア・noul 判定といった型付きの答えを確率付きで返す）を中心にしたエージェント設計をまとめる。

出発点の問いは「**LLM に KV キャッシュが無かったら、エージェントをどう設計するか？**」。この問いから、今のエージェントが検証せずに受け継いでいる6つの設計上の癖が見えてくる。お金を失うルーティング、文脈を圧迫するツール呼び出し、盲目的な圧縮、ほとんど使われないサブエージェント、状態を捨てる再起動、組み込み機能をめぐる議論、の6つである。

## I. なぜまた新しいエージェントなのか

前提は4つ。

1. エージェント部分は単純（ループ・モデル・少数のツール）
2. 既存の良い部品は再利用できる（MCP 認証などは例外的に複雑）
3. 料金が従量課金に寄るにつれ、ファーストパーティ製エージェントのコスト優位は縮む
4. **一部の機能はネイティブでしか作れない**。毎ターンの文脈組み立てを制御する必要があり、他社エージェントへのプラグインでは実現できない

4つ目が本書の主張の核。ループが単純なら、工夫の余地はループにはなく、「毎ターンモデルに何を渡すか」にある。

### A. Jev の位置づけ

Jev はコードを書くモデルではなく、その隣に置く判断層である。ハーネスが状態（目的・文脈・ルール・可能な行動・過去の行動）と決まった質問を渡すと、Jev は型付きの答えを確率付きで返す。実作業は最上位モデル・サブエージェント・ツール・決定的なコードが行う。出力が自由文ではなく型付きなので、ハーネス側で検証したり閾値で分岐したりでき、文章を解析する必要がない。

**表I: コーディングエージェントにおける Jev への問い**

| 判断ポイント | Jev への問い | 型付きの答え |
|---|---|---|
| 文脈 | このチャンクをこのクエリでどこまで見せるか | 非表示／短い要約／長い要約／全文 |
| キャッシュ | キャッシュ済みの先頭部分を再利用するか、作り直すか | noul＋確率 |
| ルーティング | このサブタスクを最上位モデルから外せるか | 選択＋コスト見積り |
| ツール | この意図に合うツールはどれか | 順位付きの上位k件 |
| 権限 | このコマンドを実行してよいか | 許可／確認／拒否 |
| セキュリティ | このタスクはどのファイルに触れるか | 機密度スコア |

### B. 全体をまとめる問い

エージェントが追記型のトランスクリプトとして作られているのは KV キャッシュのためである。先頭部分の再利用は安いが、途中を変えるとキャッシュが無効になり、それ以降を全部再処理することになる。この経済性が、明言されないままほぼ全ての設計を決めている（「KV キャッシュの専制」）。キャッシュを仮に取り除いてみると、文脈を「ためる」のではなく「組み立てる」状態明示型の設計が可能になる。同時に、「簡単な作業は安いモデルへ」のような直感的な発想が実際には失敗する理由も見えてくる。

## II. KV キャッシュが生む6つの症状

**表II: 今のエージェントが受け継ぐ6つの設計選択**

| 症状 | なぜ起きるか | 何を失うか |
|---|---|---|
| 1. ルーティングが失敗する | 大きいモデルに戻すと文脈を再処理する | 混合ルートが最上位モデルのみより高くなる |
| 2. ツールが文脈を圧迫する | スキーマをシステムメッセージに置く必要がある | 無関係なツールにトークンを使い、選択も弱い |
| 3. コンパクション | 今後の全ターンで状態が共通だと仮定 | 質問を知らない圧縮で、後で要る情報を失う |
| 4. サブエージェントが稀 | 何を渡し何を戻すかの判断が難しい | 自動的な並列化がほとんど起きない |
| 5. 再起動 | 状態を持つトランスクリプトは時間とともに壊れる | 関連する古い状態も一緒に捨てる |
| 6. 組み込み機能の議論 | 組み込み機能は常に文脈を消費する | 使いやすさと強力さの二者択一になる |

### A. ルーティングはうまくいかない

直感的な案は「最上位モデルが計画し、安いモデルが実行し、最上位モデルがレビューする」。100万トークンあたり Opus 入力 $5・出力 $25、Sonnet 入力 $3・出力 $15 で試算する。X＝文脈トークン、Y＝生成トークン、Z＝作業中の追加読み込み（コマンド出力・ファイル読み込み）とする。

- **経路1 Opus のみ**: 生成 25Y＋読み込み 5Z ＝ **25Y + 5Z**
- **経路2 Opus→Sonnet→Opus**: Sonnet の文脈読み込み 3X＋Sonnet 生成 15Y＋Sonnet 読み込み 3Z＋Opus が変更分を読み直す 5(Y+Z) ＝ **3X + 20Y + 8Z**

経路2は、セッションが長い（X が大きい）とき、書くより読む量が大幅に多いとき、またはその両方で高くなる。X=0.65, Y=0.12, Z=0.23 では **Opus のみ 4.15、経路2 6.19**。最上位モデルのまま進める方が、節約のためのルートの約3分の2のコストで済む。

（図2: 経路2の内訳は、読み込み 1.95／Sonnet 生成 1.80／Opus 読み直し 1.75／Sonnet 読み込み 0.69）

教訓は「ルーティングが間違い」ではなく、**トークン単価で評価したルーティングが間違い**だということ。評価は文脈の作り直しコストで行うべきである。ハーネスが安いモデルに全トランスクリプトではなく小さな専用文脈を渡せて、戻りで最上位モデルに補助側の出力を全部読み直させない場合に限り、ルーティングは成り立つ。

### B. ツール呼び出しは奇妙なトレードオフ

ツールは、今のターンで使うかどうかに関係なく、完全な引数スキーマごとシステムメッセージに先に宣言する必要がある。これが文脈を大きく占めるわりに、ツール選択は特に賢くならない。作業仮説は、同時にツールが多すぎること（高カーディナリティ）と、学習時と違う使い方をするツール（off-policy）の組み合わせにモデルが弱い、というもの。短い説明を先に読み込み詳細を後回しにする skills が、生のツール一覧や MCP サーバーより良い結果を出すことが多いのは、このためかもしれない。

### C. コンパクションが存在する

今後の全ターンが同じ共通状態を必要とするなら、コンパクションは完全に理にかなう。本書はその前提を疑う。汎用的な圧縮は難しく、情報を失う。次の質問が分かっていれば何を残すべきかも分かるので、質問を知った上での圧縮の方がはるかに簡単である。質問が分かる前に書いた要約は、その質問に必要だった何かを必ず捨てる。

### D. サブエージェントは微妙

モデルは期待ほど並列化しない。原因は状態管理だと推測している。親の文脈から何を渡し、各サブエージェントの発見のうち何を戻すか。この判断が高コストで間違えやすいと、モデルはそれを避ける。

### E. 再起動が存在する

再起動は、ずれたり壊れたりしたトランスクリプトへの定番の対処だが、悪い状態と良い状態を一緒に捨てる。状態を参照可能な単位で持っていれば、クリーンに始めて、まだ関係のある古いチャンクだけを必要に応じて読み込み直せる。

### F. 組み込み機能は付いていない

エージェントに組み込み機能を載せるべきかという議論がある。今は使いやすさ（機能満載のエージェント）と強力さ（Claude Code や Codex のような上級者向けツール）のトレードオフになっている。組み込み機能はどれも常に文脈を消費するからこのトレードオフが生まれる。そのコストが無くなれば、議論自体がなくなる。

## III. トークンは実際どこに使われているか

**表III: サブタスク別のトークン割合（入力が多い見方。繰り返しの読み直しも毎回数える）**

| サブタスク | 割合の目安 | 注記 |
|---|---|---|
| ファイル内容の読み込み | 30〜40% | 最大。ファイルが文脈として何度も読み直される |
| コード検索 | 10〜18% | grep・glob・一覧。出力のノイズが多い |
| コマンド出力 | 10〜20% | 失敗時にスタックトレースやログが膨らむ |
| システムプロンプト・ツールスキーマ・AGENTS.md | 5〜12% | 毎ターン払う固定費 |
| 会話の再生 | 増幅要因 | 上の全項目が繰り返し数えられる理由 |
| 推論と計画 | 5〜15% | 難しいデバッグで増える |
| コードの記述・編集 | 4〜10% | diff や str_replace の編集はコンパクト |
| ユーザーへの説明 | 2〜5% | CLI エージェントは設計上簡潔 |

目を引くのは下の方の行。コーディングエージェントの本業である「コードを書く」ことは最小クラスで、読み込みと検索が大半を占める。独立した分析も同じ方向を示す。Microsoft の fastcontext プロジェクトは、GPT-5.4 の軌跡で読み込みと検索が**ツール使用ターンの56.2%、メインエージェントの全トークンの46.5%**を占めると報告している。これが一般化するなら、最大の効率化は、より良いモデルでもより良い diff 形式でもなく、**より賢い検索**である。

（図3: 中央値の推定で、ファイル読み込み 35%／検索 14%／コマンド 15%／推論 10%／システム 8%／編集 7%／説明 3%。読み込み・検索・コマンド出力で処理トークンの約3分の2、コード記述は1割未満）

## IV. 基本層: 権限とツールルーティング

既存のどのエージェントにも、ネイティブかどうかに関係なく組み込める改善が2つある。

### A. プログラム可能な権限

エージェントが実行するすべてのコマンドについて、そもそも実行すべきかが問題になる。Claude の auto モードは分類器でこれに答えている。本書はさらに進めて、何が許されるかを**プログラム可能な問い合わせ**として表現することを提案する。重要度が高い場面では、コマンド名だけを承認するのではなく、実行前に Python やシェルファイルの中身まで読んで検査する。

```
policy "exec":
    deny  if command touches ~/.ssh or .env*
    deny  if script contents contain network egress
          and task.scope != "deploy"
    ask   if command writes outside repo root
    allow if command in read_only_set
    allow if tests/ and exit code is expected
```

### B. ツールルーターとしてのハーネス

すべてのツールスキーマをモデルに見せる代わりに、ハーネスが意図と呼び出しの間に入る。モデルは何をしようとしているかを平文で書く。ハーネスは型付きの Jev 呼び出しを重ねて最適なツール1つ（または上位数件）を選び、引数を組み立てる。モデルは数百のスキーマを文脈に持たずに済み、引数の型の誤りは黙って失敗するのではなく検証エラーになる。

## V. メタアテンション: 文脈を判断対象にする

中心となる提案は、文脈を静的なものとみなすのをやめることである。ユーザーのクエリごとに、ハーネスは Jev に2つを問う。1つは、前の文脈の良し悪し。既存の KV キャッシュを再利用すべきか、ゼロから作り直す方が安くて良いか。これを既定動作ではなく、コストを考えた明示的な判断として扱う。もう1つは、関係あるものをすべて含み、それ以外は含まない新しい文脈をどう組むか。

最も単純な形では、文脈のすべてのチャンク（各ツール呼び出しの入出力、内部推論の各部分、場合によってはユーザーとの各やり取り）に noul を付ける。後の版では、スコアの代わりに**表示段階**を付ける。

（図4: 表示段階の例。2,400行の grep 出力 → 短い要約（12件ヒット）／失敗したテストログ → 長い要約（トレース＋原因）／`auth/session.ts` → 全文（クエリに関係あり）／置き換えられた古い計画 → 非表示）

利点は、コンパクションの考え方を残したまま、主な欠点が消えること。コンパクションは質問を知る前に一度だけ圧縮する。表示段階は、質問を知った後にクエリごとに圧縮する。2,400行の grep 結果が、ある質問では関係する12件になり、次の質問では非表示になる。しかも状態から削除されることはない。

視覚的なアイデアも添えられている。grep 出力のどこが関係するかをヒートマップにできれば、予算に応じた量まで絞り込める（見た目も格好いい、とのこと）。

## VI. ルーティングとサブエージェントの再検討

動的な文脈を第一級の機能として扱えることが、ルーティングを再び成り立たせる。ハーネスがサブタスク用に小さく関係のある文脈を組めれば、安いモデルや速いモデルに振っても、そのモデルがセッション全体を読み込む必要はない。結果も、最上位モデルが読み直すトランスクリプトとしてではなく、スコア付きのチャンクとして戻せる。すべてがコストと知性の両方を考慮したものになる。

同じ仕組みでサブエージェントも使いやすくなる。本書の推測では、今のサブエージェントのコストの大部分は、ユーザーが打つような単純な指示に比べて、何の文脈を渡すかを決める作業にある。その文脈づくりが安く自動になれば、サブエージェントをもっと頻繁に使える。ユーザー向けの調整つまみも生まれる。多く払ってより速く・良い結果を得るか、控えめに回して最小コストに抑えるか。

### A. 極端な並列化

タスクの起動が安くなれば多数のタスクが同時に走り、ハーネスは並行システムの問題を抱えることになる。同期の仕組み、エージェント間通信、複数エージェントが状態を共有するときの書き込み衝突である。本書はロック付きの共有状態を提案する。読み取りと書き込みを明示的に型で分けておけば扱いやすくなる。読み取り専用のタスク同士は競合しないからである。

### B. ゴールの重複排除

`/goal` のようなゴール駆動のループでは、エージェントが同じ作業を繰り返していないかが未解決の問題である。対策の1つは、サブタスクを起動する前にサブゴールとして登録し、過去のすべてのサブゴールと照合して重複を除くこと。既に終わった作業や実行中の作業が二度起動されることはない。

## VII. ツールとスキルを原理から考える

本書は、今の「常に読み込まれるツール」と「必要時に読み込むスキル」の間にもう1層を置くことを主張する。モデルは存在を知らない行動を提案できないので、使えるものを説明する短い要約（スキルの説明文に近いもの）が必要になる。ただしその要約はシステムメッセージに常駐する必要はなく、関係するときに動的に読み込めばよい。その後ろに、必要なときに使える行動の完全なスキーマを出す仕組みを置く（ツール検索ツールに近い）。全体をつなぐ条件は、不要になった後にこれらが文脈を汚さないことである。

（図5: 段階的な開示。第1段＝1機能1行の要約、関係するときに読み込み、数百ツールでも可／第2段＝選んだ数件だけ完全な引数スキーマ／第3段＝一回限りの問い合わせ用のドキュメント。モデルは全体の安い地図を見て、選んだものの詳細にだけコストを払い、使い終わったら詳細を文脈から外す）

これがうまくいけば、II 章の組み込み機能の議論はなくなる。組み込み機能が使うまでほぼ無コストなら、エージェントは数百のツールと数千ページのドキュメントを載せて出荷できる。本書はもう1つの利点も挙げる。ほぼ無コストの連携は共同マーケティングの強い経路になり、物事がそのまま動くようになる。

### A. より良い組み込み機能

エージェントを助けると謳うコミュニティ製ツールの多くは、実際には役に立たない。本書はツール出力の圧縮ツールを例に挙げ、原因を「モデルがそれらのツールを本来理解していない」と推測する。ネイティブのハーネスなら、各ツールの使い方をモデルに教える公式プロンプト（事実上、ツールごとの組み込みサブエージェントやスキル）を同梱できる。文脈がきれいに保たれるので、ツール独自のロジックがセッションの他の部分を汚染しない。ここにもマーケティングの観点がある。その時々に人気のツールとの連携を出荷し続ければ、エージェントが話題に残り続ける。

## VIII. 条件付き指示

今の AGENTS.md は全文が読み込まれる。本書は、節ごとに条件付きで読み込むことを提案する。フロントエンドのコードを触るときはスタイルガイドを読み込み、特定のサブディレクトリ内で作業するときはそのディレクトリの「落とし穴」ファイルを読み込む。本書は、すべてのサブディレクトリに落とし穴ファイルを置くべきだとしている。

（図6: 条件付き AGENTS.md。`*.tsx` を触る？→ `style-guide.md`／`billing/` 内か？→ `billing/GOTCHAS.md`／文章を書くか？→ 文体サンプル＋禁止事項。指示はセッションではなく条件に結び付き、条件付きの断片は固定されるのでコンパクションで要約されて消えない）

これはスキルに似ているが、本書は区別する。スキルは「今これをやれ」を意味しがちで、条件付き指示は「これをどこかに覚えておけ」を意味する。後者には、スキルにない性質も要る。**コンパクションで消えないこと**である。長いセッションの序盤に読み込んだスキルは、いずれ圧縮・要約されて消える。条件に結び付いた指示は、条件が成り立つたびに読み込み直される。

普通のチャットでも同じ必要がある。要約を頼まれたら好みの形式を読み込み、本人の文体で書くよう頼まれたらサンプルと禁止事項のリストを読み込む。コードを頼まれたらスタイルガイドと「アサーションを大量に足さない」という注意を読み込む。

### A. 構造化スキル

ハーネスがどこまでプログラム可能になるか次第で、スキルは指示だけでなく振る舞いの変更も運べるようになる。Claude Code のスキルフックに近いが、もっと強力なものである。本書が指摘する今のフックの制約は、一度追加するとセッション中ずっと残ること。構造化スキルは、きっかけとなった条件に合わせて振る舞いを付けたり外したりする。

### B. 再帰的言語モデル

関連する方向として、再帰的言語モデルのアプローチがある。エージェントの状態の多くを、トランスクリプトの文章ではなく明示的な変数として扱う。状態が名前付き変数で保持される世界は、「文脈ウィンドウにたまたま残っているもの」が状態である世界より、かなり整理されたものになりうる。

## IX. セキュリティを考慮したルーティング

今のルーティングは難易度とコストを軸にしている。本書は第3の軸として**信頼**を加える。低コストの提供者が出すオープンウェイトモデルの一部は、最上位モデルの API より劇的に安い。一方で、そうした提供先を通るデータが非公開のまま保たれない懸念もある。提案は、各サブタスクがどの種類のファイルに触れそうかを見積もり、ファイル種別にポリシーを付け、それに従ってサブタスクを振り分けることである。

**表IV: データの機密度によるルーティング**

| 触れそうなファイル | ポリシー | 使えるモデル |
|---|---|---|
| 公開ドキュメント、OSS 依存 | open | 何でも可、安い順 |
| アプリケーションコード | standard | 審査済みの提供者 |
| 秘密情報、env、インフラ設定 | restricted | ファーストパーティの最上位モデルのみ |
| 社外秘の研究コード | custom | 指定ベンダーを除外 |

最後の行は、本書のより広い論点を表している。ルーティングの理由は難易度とコストだけではない。チームが自社のモデル研究のために特定ベンダーのモデルを避けたり、安全上重要な作業で特定の提供者を避けたりすることもある。ルーティングがポリシーで決まるようになれば、こうした方針は各自の心がけではなく設定になる。

## X. バックグラウンド処理

本書は、人気のあるいくつかのエージェントワークフローに共通して現れつつあるパターンを挙げる。

- 作業の進行に合わせて並行更新される HTML ページ
- 「生成ではなく理解が新たなボトルネック」という主張
- バックグラウンドでの評価データ生成
- 少数の大きな絵とごく少ない言葉でシステムを説明する ELI5 スキル
- 長い実行中にスマホから確認できる、スクショとメモ付きの小さな進捗ページをエージェントに維持させる習慣
- 本番の実トラフィックを候補モデルにも流し、切り替え前に約1日かけて評価を自動生成する運用パターン

共通点は、通常のコーディング作業の拡張としてバックグラウンドで動き、現在のコードベースの状態に対する**読み取り専用の関数**であること。あるベンダーのエージェントに別ベンダーの成果物をレビューさせるクロスモデルレビューも同じ型に当てはまる。

（図7: 明示的な状態の上でのバックグラウンド処理。メインエージェントが書き、共有の検索層が関係するファイル・シンボル・diff を1回だけ見つける。クロスモデルレビュー、評価生成、ELI5 解説・クイズ、進捗ページ、ミクロ世界シミュレーションといった読み取り専用タスクがそれを共有し、ロックを奪い合わない）

ここで Jev の主張が実を結ぶ。Jev 中心のハーネスは、何が文脈にあるか、各操作が読み取りか書き込みかを厳密に扱う必要がある。コード変更に関係する情報を見つけるのは簡単ではない。その検索を各タスクが繰り返すのではなく全バックグラウンドタスクで共有すれば、実行はずっと安くなり、もっと多くのタスクを回しても採算が合う。III 章の「検索がトークン予算の大半を占める」という結果からすると、検索の共有は単独で最大の節約になる。本書の言葉では、読み取りと書き込みを明示することが、いずれエージェントに超能力を与える。

## XI. 組み込み機能の候補

本書の最後に、ネイティブに統合できるオープンソースプロジェクトが挙げられている。それぞれに、Jev 中心のハーネスならどう使うかの設計メモが付く。

**表V: 組み込みツールの候補**

| プロジェクト | 役割 | ネイティブでの使い方 |
|---|---|---|
| headroom | 文脈の圧縮 | 圧縮後に必要な事実が残っているか分類器で確認 |
| rtk | ツール出力の圧縮 | モデルが理解できるよう公式プロンプトを付ける |
| ast-grep | 構造検索 | マニュアルを1回読み込み、N個のクエリを生成し、関連度で絞る |
| ast-outline | 構造のアウトライン | 階層的な呼び出しで、調べる部分木を選ぶ |
| fastcontext | リポジトリ探索用サブエージェント | これに振るか、その検索を構造で置き換える |
| fff | パスと内容の検索 | メモリ内索引・頻度順。長いセッションでは ripgrep より速い |

## XII. 結論

設計メモの主張は、言うのは簡単で実行は難しい。コーディングエージェントは単純なループであり、工夫の余地はループにはない。効くのは、ハーネスが毎ターンモデルの前に何を置くかである。今はその判断が、KV キャッシュの経済性に合わせた追記型トランスクリプトという既定動作で決まっている。

思考実験としてキャッシュを取り除くと、見慣れた6つの挙動が違って見える。ルーティングが失敗するのは安いモデルが弱いからではなく、文脈が再処理されるから。ツールが文脈を圧迫するのは、先に宣言しなければならないから。コンパクションが情報を失うのは、質問を知る前に圧縮するから。サブエージェントが稀なのは、状態を渡すのが難しいから。再起動は悪い状態と一緒に良い状態も捨てる。組み込み機能の議論は、組み込み機能が永遠に文脈を消費するからこそ存在する。

提案するハーネスは、1つの変更で6つすべてに対処する。状態を明示的かつ型付きにし、文脈・ルーティング・ツール・権限を Jev がクエリごとに決めることである。チャンクは表示段階で評価される。ルーティングは文脈の作り直しコストで見積もられる。ツールは段階的に開示される。指示は条件に結び付く。バックグラウンドタスクは1回の検索を共有する。どれもより良いモデルを必要としない。必要なのは、文脈ウィンドウを「偶然たまるもの」ではなく「意図して組み立てるもの」として扱うことである。
