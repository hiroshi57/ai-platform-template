# ECDYSIS 診断ガイド（横断的失敗集約＋失敗の帰属）

> 出典: ECDYSIS（arXiv:2609.11677, 2026-09）——「ランタイムハーネスを効率よく・過学習させずに
> 進化させる」訓練フレームワーク論文。要約すると「失敗を1件ずつ直すと**モデル固有適応**に
> 過剰適応して汎化が壊れる。**複数タスクで再発する失敗**だけを体系的欠陥の証拠とし、
> 診断（仕様）と実装（コード修正）を分けろ」。
> このファイルは harness-retro の Step 3（仮説形成）と Step 4（提案作成）で、
> `harnessdev-checklist.md` の直後に当てる診断ガイド。難しい理論は読まなくてよい。
> HarnessDev が「**何が壊れるか**（4落とし穴）」なら、ECDYSIS は「**どう切り分け・直すか**」を与える。

## 前提となる考え方（1行ずつ）

- 観測された失敗は2種類ある。**モデル固有適応（model-specific accommodation）**＝そのモデルの
  クセ由来か、**ハーネス修復（harness-level repair）**＝仕組み自体の体系的欠陥か。直す価値があるのは後者。
- 失敗1件では両者を区別できない。**別タスクでも再発している**ことが、体系的欠陥の強い証拠になる。
- t = coding-agent の全修正判断のうち、モデル固有適応が占める割合。t が高いほど過剰適応。
  論文実測で Self-Evolution=60.0% → ECDYSIS=45.5%（-14.5pt）に下げると汎化が改善した。
- 診断（何を直すかの仕様）と実装（実際のコード修正）は分ける。混ぜると忖度修正が紛れ込む。

## チェックA: その失敗、別タスクでも再発しているか（横断再発）

> 対になる HarnessDev チェック: **新規軸**（既存チェックにない。Step2「最低2件以上の根拠」を task 軸で定量化）。

**論文の知見**: 単一タスクの繰り返し失敗は、その失敗機構が他タスクへ一般化する証拠にならない
（§3.3）。ECDYSIS は「**2つ以上の異なるタスクをまたぐ失敗グループ**」を優先的に体系的欠陥とみなす。

**retroでの当て方**:
- 同じ `reason_code` / `escalation_reason` が、**異なる task_id** で起きているか数える。
  分離ファイル形式（v2）の場合:
  ```bash
  # 同一 reason_code が「いくつの異なるタスクディレクトリ」で出ているか
  grep -rl '"reason_code": *"<対象>"' .claude/harness-logs/<project-slug>/ \
    | sed -E 's#.*/([0-9.]+)/[^/]+$#\1#' | sort -u | wc -l
  ```
  ログが `raw-hook-payload.json` 1本だけの形式（v1、SKILL.md Step1 の注記参照）の場合は、
  ファイル分離されていないのでタスクディレクトリ名で数える:
  ```bash
  grep -rl '"reason_code"' .claude/harness-logs/<project-slug>/ \
    | grep 'raw-hook-payload.json' \
    | sed -E 's#.*/([0-9.]+)/[^/]+$#\1#' | sort -u | wc -l
  # 各 raw-hook-payload.json を cat して reason_code の値と task_id を突き合わせる
  ```
- 別タスク **2件以上** → 体系的欠陥候補（harness-proposals へ）。
- 単一タスクの再試行のみ → 「弱い証拠」。提案化せず観察継続（retries.log にだけ残す）。

**提案の型**: 「この1タスクで詰まったから直す」ではなく「A・B 両タスクで同じ機構が壊れている」まで示す。

## チェックB: その修正、モデル固有適応になっていないか（帰属の切り分け）

> 対になる HarnessDev チェック: **③ co-adaptation** と **④ 過学習**。両者を「帰属ラベル」で明示的に切り分ける。

**論文の知見**: 個別失敗に反応した修正は、正当な行動選択肢をモデルのエラー回避のために
削り、有効行動空間を狭めて汎化を壊す（§8.3）。「特定タスクの正解」をグローバルな
ハーネス制約に昇格させてしまうのが典型。

**retroでの当て方**: 提案しようとしている変更を、次の3分類で自問する。
- `harness` = 仕組みの体系的欠陥（state 同期漏れ・エンティティ解決・ツール順序など）→ **直す**。
- `model` = そのモデル固有のクセ → ハーネスをそれに合わせて歪めない。プロンプト微調整に留める。
- `ambiguous` = 証拠不足 → 横断再発するまで保留。
- 特に「特定モデルでだけ落ちる（Opusは通るがCodexで落ちる）」失敗を、全体ルールや
  グローバル禁止に昇格させようとしていないか。それは `model` 側の可能性が高い。

**提案の型**: 帰属を明記する。`model` と判断したら skill/CLAUDE.md を書き換えず、対象を絞る。
`harnessdev-checklist.md` チェック3（co-adaptation）・チェック4（過学習）と同じ危険を、
「帰属ラベル」で明示的に切り分けるのがこのチェックの役割。

## チェックC: 根本の runtime 制約を捉えているか（表層の暗記ではなく）

> 対になる HarnessDev チェック: **④ 過学習**（「別文脈でも効くか」を、抽象化の観点で具体化）。

**論文の知見**: Retail と Airline のように表層が違うタスクでも、再発する相互作用構造は共通する
（状態更新後の再照会、副作用前のエンティティ解決、下流ツール呼び出し前の前提条件検証など、§8.1）。
効果的な修正は「タスク固有の失敗の暗記」ではなく「根底の runtime 制約」を捉えるべき。

**retroでの当て方**:
- 提案が「このタスクのこの入力を弾く」になっていないか。より抽象化して
  「状態更新後は再照会する」「副作用のある操作の前に曖昧なエンティティを解決する」
  「下流ツール呼び出し前に必要な依存情報を検証する」のような**再利用可能な制約**に言い換えられるか。
- 言い換えられるなら、その修正は未知の構造的類似タスクにも効く（汎化する）。

**提案の型**: 修正を「1タスクの対症療法」から「runtime 制約の一般形」へ引き上げてから提案する。
引き上げられないなら案件ローカルに留める（HarnessDev チェック4と同趣旨）。

## チェックD: 診断と実装を分けているか／バッチでまとめているか（FDCR・効率）

> 対になる HarnessDev チェック: **② 失敗を読んで直す**（テスト量でなく、診断→1修正→再検証の質）。

**論文の知見**: ECDYSIS は失敗を1件ずつ coding-agent に投げず、1ラウンド分をまとめて
1回の修正仕様にする（バッチ集約）ことでコストを最大約70%削減。さらに FDCR で
Analyst→Critic→Moderator が仕様を練ってから実装に渡す（§3.4）。診断と実装の分離が肝。

**retroでの当て方**:
- 複数の再発失敗を、**バラバラに何度も**提案していないか。1回の retro で横断集約して
  **1本の提案**にまとめる（TerminalBench の教訓「1提案＝1変更理由」と両立させる：
  理由は1つに絞りつつ、根拠となる失敗は複数タスクから集める）。
- 提案を出す前に、軽い自己批判を通す（Critic 役の代行）:
  - トリガーが広すぎないか
  - 正当な動作を巻き込んで止めていないか
  - runtime 契約に違反していないか
  - 既存の成功タスクを回帰させないか

**提案の型**: 「診断＝何を直すかの仕様」を先に固め、diff（実装）はその後。提案本文に
上記4点の自己批判結果を1行ずつ添える。

## まとめ（この順で自問する。SKILL.md Step3 の A/B/C/D と同一）

A. その失敗は**別タスクでも再発**しているか（単一タスクのみは弱い証拠→保留）
B. その修正は `harness` 欠陥か `model` 固有適応か（model なら skill を歪めない）
C. タスク固有の暗記でなく再利用可能な **runtime 制約に抽象化**できているか
D. 複数の再発をバッチで**1本にまとめ**、診断→実装の順で Critic 4点の自己批判を通したか

4つとも通ったものだけを `harness-proposals/` に出す。
`harnessdev-checklist.md`（何が壊れるか）→本ファイル（どう切り分け・直すか）の順で当てるとよい。
