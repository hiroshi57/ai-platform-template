## TL;DR（3行要約）

- **主張**: ① 教える側に「正解」を見せると、学ぶ側は近道を覚えて汎化しない。手順のガイドの方が効く ② 手本を集めたときの成功率は、その手本の有用さを予測しない ③ 判定・レビューをする側のモデルが弱いと、介入が増えて結果は悪くなる。
- **提案**: A. retro で skills / rules / memory に足す内容は、特定タスクの答えではなく**再利用できる手順**で書く。B. 蒸留層（skills）や将来の学習データの手本は、APPROVE / 成功率ではなく**手順の証跡があるか**で選ぶ。C. Reviewer / 判定器には **Worker と同等以上**の強さのモデルを使い、介入過多を retro で監視する。
- **効果**: どれも**ルール文書の追記だけ**で実装できる。新しい基盤もモデル変更も不要。既存の [`decision-boundaries.md`](../.claude/rules/decision-boundaries.md) ルール5（結論ではなく証拠を渡す）、[`memory-curation.md`](../.claude/rules/memory-curation.md)（記憶の提供形式）、[`judge-rubric.md`](../.claude/rules/judge-rubric.md)（判定器）を補う。

## 1. 背景: 論文の要点と本ハーネスとの対応

論文は、分野向けに最適化したハーネスを**学習のときだけ**使い、その振る舞いをモデルの重みに移す方法（ハーネス蒸留）を提案する。生徒モデルの各行動を、実行前にレビュー役のエージェントが「参照ハーネス K」（ツール・ミドルウェア・skills・memory を、レビュー用のガイドに書き換えたもの）を見て、そのまま通す（PASS）か最小限の修正に置き換える（REPLACE）。その記録で SFT をかける。

本提案で使うのは、その中の**対照実験**（§4.4 表3、§付録 F 表8）の結果である。

|---|---|---|---|---|

## 2. 現行運用の不足点

### 2.1 retro の提案が「答え」になりうる
[`harness-retro.md`](../.claude/rules/harness-retro.md) と CLAUDE.md §7 は、提案を「diff 形式＋根拠ログ＋期待効果」で出すと定めるが、skills / memory / rules に**足す中身**の形は問わない。「タスク 43.3.1 では X ファイルの Y 行を Z にすれば通った」という内容でも、規則上は正しい提案になる。論文の知見1は、こうした答え型のガイドが、学ぶ側に汎化しない近道を覚えさせることを示す。

### 2.2 手本の選び方が決まっていない
[`memory-curation.md`](../.claude/rules/memory-curation.md) の二層構造は、生ログから蒸留層（skills）を作ることを前提にしている。どのログを手本にするかの基準がないため、APPROVE されたタスクのログが無条件で選ばれやすい。論文の知見2・3によれば、成功したかどうかと、手本として役に立つかどうかは別である。

### 2.3 判定器モデルに下限がない
`review.json` の `judge.model` は記録するだけで、Worker との強さの関係は問わない。提案7 の「アンカーを先に直す」は、判定器が十分に強いことを前提にしている。弱い判定器では、アンカーを直しても判定が悪化しうる（知見4）。
