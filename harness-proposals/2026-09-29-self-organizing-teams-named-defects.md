## 1. 背景: 論文の要点と本ハーネスとの対応

論文は、メンバー固定のエージェントチームが、過去の協働ログから「チームワーク戦略」（役割・会話の段階・参加者・情報の流れ・統合の仕方）を学習する手法 SAT を提案している。本番では学習済みの戦略を全部実行して候補を作り、1体の審査役が1つを選ぶ。

| 論文の知見 | 出典 | 本ハーネスの現状 | ギャップ |
|---|---|---|---|
| 正解の候補を作れても、選べないことが多い（カバレッジ 87.9% に対し正答率 72.8%） | 表2, §4, §7 | retro は APPROVE 率・再発率・κ を見る | **候補が複数あったとき、正しい候補があったのに選べなかった件数を数えていない** |
| 審査役は自分で問題を解かず、候補の記録（certificate）の品質だけを監査する | 付録 D.1 | `judge-rubric.md` ルール4: 自己申告を証拠にせず、外部証跡を `evidence_ref` で指す | 近い。ただし「判定者が自分で作り直した案と比べて下げる」ことは禁止されていない |
| 落とす・下げるのは、具体的な局所的欠陥（飛躍しているステップ、指摘できる計算ミス、漏れているケース、根拠のない仮定）を名指ししたときだけ。「答えが違う気がする」「他の候補と食い違う」は欠陥として数えない | 付録 D.1 | スコアごとに `evidence_ref` はあるが、**満点でない理由（どこが欠陥か）の記録は必須でない** | 差し戻しの理由が「不安」でも規則上は通る |
| 全候補の監査を書き終えてから決める。答えの多数決は、欠陥ゼロの候補が複数あるときの同点処理にだけ使う | 付録 D.1 | 手順の定めなし | 最初に目についた問題で判定が固まりやすい |
| 討論（Debate）はラウンドを重ねると正しい少数意見を潰す。GPQA の例では、誤った多数派が全員一致の誤答になった | §1, §4, 付録 図10 | Claude と Codex のクロスレビューで意見が割れたときの扱いが未定義 | 多数決や「強い口調の方」に寄る余地がある |
| 正誤を見分けやすいタスクほど、チームの伸びが大きい（Spearman ρ=0.90, p=0.005） | §5, 図6 | — | 付録 B（次の候補）で扱う |

**含意**: 本ハーネスは、判定の**根拠**（外部証跡・`evidence_ref`）はもう揃えている。足りないのは、**スコアを下げる理由の形**（A）と、**判定そのものの失敗を測る数字**（B）。

## 2. 現行運用の不足点

### 2.1 スコアを下げる理由が記録されない
`scores[].evidence_ref` は「どの証跡を見たか」を指すが、満点でないときに「その証跡のどこが欠陥か」は書かなくてよい。そのため、REQUEST_CHANGES の理由が「全体的に不安」「自分ならこう書く」でも規則上は通る。Worker は何を直せばよいか分からず、差し戻しの後のリトライが新しい情報を伴わなくなる（[`decision-boundaries.md`](../.claude/rules/decision-boundaries.md) ルール1と衝突する）。

### 2.2 判定器どうしのぶれの原因が分からない
提案7の κ 測定で一致度が低くても、今の `review.json` からは「同じ欠陥を見て重みの付け方が違った」のか「片方が欠陥を見つけていない」のかを区別できない。欠陥が名指しされていれば、欠陥単位で突き合わせられる。

### 2.3 「選び間違い」が数字に出ない
リトライ、REQUEST_CHANGES の後の amend、Claude と Codex の並列実装などで、1つのタスクに候補が複数できることがある。今の retro は最終結果の APPROVE / REQUEST_CHANGES しか見ないので、「前の候補の方が正しかったのに差し戻した」「正しい候補がなかった」の区別がつかない。前者なら直すのは判定側、後者なら生成側（Worker の状態・選択肢・契約）である。

#### diff 1: `.claude/rules/judge-rubric.md`

```diff

+++ b/.claude/rules/judge-rubric.md
@@ ## ルール（MUST） @@
 5. **rubric を版管理する。** rubric を変えたら `rubric_version` を上げる。版が違う判定を同じ母集団で集計しない。
+6. **スコアを下げるときは欠陥を名指しする。** 観点を満点未満にするときは、その観点の `named_defects` に
+   1件以上の欠陥を書く。欠陥は、外部証跡の場所（diff の hunk、`commands.stdout.log` の行）と、
+   次のどの種類かで書く。
+   - `unsupported-step`: 変更や主張が、前の証跡から導けない（テストが通ったことを示す行がない、など）
+   - `missing-case`: DoD の項目・分岐・エラー経路のどれかに対応する証跡がない
+   - `wrong-as-written`: 書かれたとおりに読むと誤っている（テストの期待値が逆、条件の取り違え、など）

+   「他の判定者の結論と違う」。判定者は Worker の成果物を自分で作り直して比べない。
+7. **全観点を監査してから判定する。** まずすべての観点について `named_defects`（空でもよい）とスコアを書き、
+   その後で verdict を決める。途中の観点で結論を決めない。
+8. **判定者の多数決で決めない。** 判定者が複数いて結論が割れたときは、各判定者の `named_defects` を
+   突き合わせる。どの判定者の欠陥も成り立たないと確認できた観点だけを満点にする。

+   REQUEST_CHANGES は、`named_defects` が1件以上あるときだけ出せる。
@@ ## review.json の必須フィールド（review.v1 追加分） @@
```

```diff
+
+## 提案9: 生成と選択を分けて測る（arXiv:2609.22682）
+
+> **起源**: 提案 `harness-proposals/2026-09-29-self-organizing-teams-named-defects.md`（提案 B）
+
+実証結果: エージェントチームが作った候補の中に正解がある割合（カバレッジ）が 87.9% でも、
+最終的に正解を選べた割合は 72.8% にとどまった。正解を作る失敗と、正解を選ぶ失敗は別の失敗で、直す場所も違う。
+
+### 対象
+
+1つのタスクに、判定を受けた候補が2つ以上あるもの（リトライ、REQUEST_CHANGES の後の amend、
+複数 Worker・複数モデルによる並列実装）。候補ごとの `worker-report` と `review` は上書きせず、
+`worker-report.<n>.json` / `review.<n>.json` として逐語で残す（`memory-curation.md` ルール4）。
+
+### 「正しい候補」の判定（コードで決める。LLM に判断させない — `decision-boundaries.md` ルール2）
+
+次をすべて満たす候補を「正しい候補」とする。
+- `commands.stdout.log` で、その候補の検証コマンドが全て PASS している
+- その候補の `named_defects` のうち、人間の再採点（提案7）で成り立つと確認されたものがない
+- 採用された候補なら、APPROVE の後にインシデントが起きていない（提案8）
+
+### チェック項目（retro のたびに実施）
+
+7. **候補カバレッジと選択正答率**: 対象タスクについて次を数える。
+   - 候補カバレッジ = 正しい候補が1つ以上あったタスクの割合
+   - 選択正答率 = 最終的に採用した候補が正しい候補だったタスクの割合
+   - 選択ロス = 候補カバレッジ − 選択正答率
+
+### 判断
+
+- 選択ロスが大きい（正しい候補があったのに選べていない）ときは、判定側を直す。
+  診断順序（提案8）の 3（契約・rubric のアンカー）と 4（閾値・経路）を先に確認する。
+- 候補カバレッジが低い（正しい候補がそもそもない）ときは、生成側を直す。診断順序の 1（状態）と 2（選択肢）から確認する。
+- 対象タスクが10件未満の retro では、率ではなく件数と個別の事例だけを記録する（率で判断しない）。
```
