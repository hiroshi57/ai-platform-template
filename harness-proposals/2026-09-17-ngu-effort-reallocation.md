## TL;DR（3行要約）

- **主張**: NGU は「RL は簡単な問題ばかり改善し難問を放置する**マタイ効果**を起こす。原因はシグナル損失でなく**計算配分の非効率**。簡単な所への浪費をやめ難所へ動的再配分せよ」を実証。本ハーネスの **effort/リトライ配分**にも同型の偏りが起きうる。
- **提案**: ①retro に「effort が簡単タスクに偏っていないか」の**マタイ効果チェック**を追加（A）②タスク難易度を「着手直後」でなく「**ハーネス適応後**（context 読込・1回目検証後）」で測る運用を明記（B）③リトライを**ハードキャップの手前で "諦め判断" を確率化**（advisory、上限は不変）（C）。
- **効果**: いずれも**既存ログ（harness-logs / worker-report）の集計と Lead 運用の微調整で実装可**、新規基盤・モデル変更不要。§4 で実測して確認する。

## 1. 背景: NGU と本ハーネスの構造対応

NGU の中核は「**固定の計算（$K$ 個の補完）を全問題に等配分すると、簡単な問題を過剰サンプルし難問を放置する（マタイ効果）**。解けるまで諦めず、非同期インフラで簡単な所から難所へ計算を再配分せよ（シグナル効率）」。

本ハーネスで「計算」に対応するのは **effort（medium/high/xhigh）・turns・リトライ回数**という有限リソース。同型の偏りが起きうる:

| NGU（論文）| 本ハーネス | 対応の性質 |
|---|---|---|
| マタイ効果（簡単な問題ばかり改善）| effort が「通りやすいタスク」に均等配分され、難タスクが慢性的に REQUEST_CHANGES/escalate | 同型（累積的優位）|
| シグナル損失 ≠ 主因 | 「難タスクはモデルを強くすれば解ける」だけが主因ではない | 類似 |
| シグナル効率（計算あたり性能）| turns/effort あたりの APPROVE 率を最適化する | 同型 |
| 固定 $K$ の無駄 | 全タスク一律 effort=medium（frontmatter 既定）の無駄 | 同型 |
| NGU: 解けるまで諦めない（確率 $p$）| リトライを諦める判断を確率化（ハードキャップ手前）| 類似（ただし上限は保持）|
| 非同期インフラが再配分の鍵 | 並列 Worker / worktree が再配分の前提 | 同型 |
| ハーネス認識マタイ効果（適応後に難易度測定）| 難易度は「context 読込・初回検証後」に測るべき | **同一原則** |
| 密な評価シグナルへ（スカラー不十分）| self_review 5 rule の evidence（密な検証）を単一 APPROVE より重視 | 同一方向 |

**含意**: 本ハーネスは既に「非同期（並列 Worker）」「密な評価（self_review evidence）」を持ち、NGU の前提条件を満たす。欠けているのは **effort/リトライが簡単タスクに偏る退行の検知**と**適応後の難易度測定**である（§2）。

## 2. NGU が示唆する、現行運用の不足点

### 2.1 effort の偏り（マタイ効果）が観測されていない

現行の effort 制御は frontmatter 既定 `medium`、`xhigh` は呼び出し側（Lead）が選ぶ（Worker frontmatter「Effort 制御」）。**「どのタスクに高 effort を割いたか」と「その結果 APPROVE できたか」の相関は集計されていない**。NGU の警告（図2: 一律配分は難問を伸ばさない）に照らすと、Lead が無意識に「通りやすいタスク」へ高 effort を割き、慢性的に失敗する難タスクには通常 effort のまま放置する偏りが起きうる。これは retro で検知すべき退行。

### 2.2 難易度を「着手直後」に判定している

NGU の重要発見は **ハーネス認識マタイ効果**（和訳 §6）: 新規プロンプト/ハーネスでは、初期のステップは「タスク改善」でなく「プロンプトへの適応」であり、**適応前の難易度判定は誤る**。本ハーネスで対応するのは「task 記述文だけでタスク難易度を見積もる」こと。Worker が `context`・`contract`・対象ファイルを読み、1 回目の検証を回した**後**でないと真の難易度は分からない。現行に「適応後の難易度再評価」の観点がない。

### 2.3 「諦め」がハードキャップの一点張り

現行は「同じ原因の自動修正は最大3回、3回目で escalate」（Worker frontmatter「エラー復旧」）。NGU は「難問を一律に諦めると最難問が永久に伸びない。**確率 $p$ で継続**し、時折多く試す」ことで最難問を解いた（和訳 §4）。本ハーネスの3回上限は**安全・コスト上の正当な設計**なので維持するが、その**手前**で「1回目と2回目の失敗が別原因なら、まだ探索余地がある」といった**継続/諦めの判断を機械的な回数だけでなく多様性で条件づける**余地がある。

## 3. 提案（A / B / C）

### 提案 A: retro に「effort マタイ効果チェック」を追加（advisory）

- **変更**: `harness-retro.sh --check` の出力に、直近 N タスクの **effort_applied × review 結果**のクロス集計を advisory 追加。「high/xhigh effort が first-pass APPROVE 率の高い（＝もともと簡単な）タスクに偏っていないか」「慢性 REQUEST_CHANGES タスクが低 effort のまま放置されていないか」を警告する。
- **NGU 根拠**: 和訳 §2（マタイ効果）・§3（シグナル効率＝計算あたり性能）・図2/3。
- **データ**: worker-report.v1 の `effort_applied` / `effort_sufficient` / `turns_used`（既存フィールド）＋ review.json。**新規計装不要**。
- **対象外の尊重**: effort の自動変更はしない（Worker は effort を動的変更しない、frontmatter 契約を維持）。Lead への**可視化のみ**。

### 提案 B: 「ハーネス適応後の難易度」で effort を再配分する運用を明記

- **変更**: Lead が effort/turns を割り当てる際、**task 記述だけでなく「Worker が context/contract/対象ファイルを読み初回検証を回した後」のシグナル**（初回 self_review の verified 数、初回検証コマンドの失敗種別）で難易度を再評価してよい、と運用ルールに明記。難タスクへ turns/effort を後追いで再配分する。
- **NGU 根拠**: 和訳 §6「ハーネス認識マタイ効果」（適応後に難易度測定すべき）。
- **対象外の尊重**: `xhigh` を選ぶのは呼び出し側（Lead）という既存契約を維持。Worker が自己昇格しない。

### 提案 C: 「諦め判断」を回数だけでなく失敗多様性で条件づける（advisory・上限不変）

- **変更**: エラー復旧で、**ハードキャップ（3回）は変えず**、その手前の継続判断に「**直近の失敗が同一 `normalized_error_signature` か否か**」を advisory シグナルとして加える。同一原因の反復（＝停滞）は早めに advisor-request、異なる原因での失敗（＝探索が進行中）はキャップ内で継続、という判断材料を明文化する。
- **NGU 根拠**: 和訳 §4（諦めを確率化して最難問を解く）・§3（同一の失敗反復はシグナルを増やさない）。既存の advisor 判定「同じ原因の失敗が2回続いた → `retry-threshold`」と整合し、**"同じ原因" の検知を强化**する方向。
- **対象外の尊重**: 自動修正3回・相談3回・1タスク相談上限の**数値は一切変更しない**。追加するのは「継続 vs 相談」の判断材料のみ。

## 4. 効果測定（承認後・各フェーズで実測）

NGU の数値は LLM 学習ドメイン固有であり本ハーネスに転用保証しない。以下を実測する。

| 指標 | 測定方法 | 期待方向 |
|---|---|---|
| effort–難易度の相関 | `effort_applied` × first-pass APPROVE 率のクロス集計 | 偏りの可視化（ベースライン把握）|
| 慢性失敗タスクの effort | 2回以上 REQUEST_CHANGES/escalate したタスクの平均 effort | 上昇（難所へ再配分）|
| turns あたり APPROVE 率 | APPROVE 数 / 総 turns_used（提案前後 各20タスク）| 上昇（シグナル効率）|
| 同一原因反復の早期相談率 | 同一 error_signature 2回目での advisor-request 発火率 | 上昇（停滞の早期検知）|

- 効果が確認できないフェーズは**その時点で停止**し撤回してよい（各提案は独立）。

## 5. 未解決論点（フェーズ着手前に個別確定）

- **P-1**: 「タスク難易度」の代理指標（初回 self_review verified 数 / 初回検証失敗種別 / files 数・行数）をどう定義するか。NGU の pass@k 難易度バケットに相当。
