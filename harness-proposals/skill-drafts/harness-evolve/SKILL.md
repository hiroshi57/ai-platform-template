# Harness Evolve（ハーネス自己進化サイクル・承認ゲート付き・1回回し切り）

あなた（Claude）はこのセッションでは **進化サイクルの司令塔**であり、**harness本体の編集者ではない**。
対象プロジェクト: $ARGUMENTS （省略時はカレントリポジトリ）

設計の元ネタ: ECDYSIS論文（arXiv:2609.11677）の Algorithm 1（進化ループ：
実行→失敗集約→FDCR診断→修正→検証→採用/棄却→凍結）。本スキルは論文と2点で変える:
1. **完全自律 → 承認ゲート付き**: 候補の自動採用・自動凍結はせず、採用の最終判断と実反映は人間。
2. **多ラウンド自動継続 → 1サイクル回し切り（single-pass）**: 1回のサイクルを最後まで回したら
   報告して止まる。続けるかどうかは人間が判断し、再実行する（暴走防止と、1変更ごとの効果確認のため）。

**旧 harness-retro との関係**: どこがボトルネックかを明確にする診断は旧に任せる。本スキルは
その診断（ボトルネック特定）を起点に、「試す→測る→採用/棄却を提案する」を1回分だけ回す。

## 大原則（最優先で守ること）

1. **回すのは自動、採用は人間。** いつ回すか・何を測るか・どの提案を候補にするかは自由に判断してよい。
   一方、CLAUDE.md / AGENTS.md / skills への**実反映（採用）は必ず人間承認**。自動採用・自動凍結はしない。
2. **診断は harness-retro に委譲する。** 失敗の集約・FDCR・HarnessDev/ECDYSIS チェックは本スキルで
   再実装せず、harness-retro スキルを呼ぶ。本スキルは「ループの外枠」と「採用可否の会計」に徹する。
3. **触ってはいけない領域**（harness-retro と同一）:
   - CLAUDE.md/AGENTS.mdの「禁止事項」セクション全般
   - コミットメッセージ規約・ブランチ運用ルール
   - 各案件 Plans.md の `cc:*` マーカー
   - secrets 系ファイルの内容
4. **1サイクル1変更理由。** 検証で「何が効いたか」を切り分けるため、1サイクルで試す提案は
   原則1本（複数同時採用は効果の帰属が不能になる。HarnessDev の教訓）。複数直したいなら
   サイクルを分けて（人間が再実行して）1本ずつ回す。

## Step 1: サイクル開始判定（①いつ回すか）

1. 対象リポジトリルートとプロジェクト slug を特定（`git rev-parse --show-toplevel`）。
2. `bash scripts/harness-retro.sh --check` を実行し、再発検知の一次情報を得る。
3. **ECDYSIS の横断再発条件**で回すべきか判定する（ecdysis-cross-instance.md チェックA と同基準）:
   - 同一 `reason_code`/`escalation_reason` が **別タスク2件以上**で再発 → サイクルを回す価値あり。
   - 単一タスクの再試行のみ → 「弱い証拠」。今回は回さず観察継続と報告して終了してよい。
4. `/harness-release` の直前は、再発が無くても1サイクル回す（憲法で必須化されているチェック）。

---

## Step 2: ベースライン記録（進化台帳を開く）

`<repo>/harness-proposals/harness-evolution-log.md` を用意する（無ければ新規作成。これは台帳であり
harness本体ではない）。今サイクルのエントリを追記し、**変更前のベースライン**を記録する。

- **harness スナップショット**: 対象になりうるファイル（CLAUDE.md/AGENTS.md/skills）の現在の git ハッシュ
  （`git rev-parse HEAD`）と、直近で凍結したハーネス状態のタグ/コミット。
- **Jtrain 代理指標（変更前）**: 自動ベンチが無い環境なので、直近 N タスク（既定 N=10、または直近1か月）の
  harness-logs から次を集計する。これを「訓練スコアの代理」とする。
  - 成功率代理: `status: escalated` でないタスクの割合
  - 安定度: 同一 reason_code の横断再発件数
  - 効率: `turns_used` の中央値、final evaluation tokens の合計/中央値
- 台帳に「サイクル日付 / ベースライン指標 / スナップショット」を記録する。

> **ノイズ注意（HarnessDev チェック④）**: これらの指標はブレる。単発の改善を過信せず、
> 後段の採用判断では「別タスクでも成り立つか」を必ず併せて見る。

---

## Step 3: ボトルネック特定・提案（②③④＝harness-retro に委譲）

harness-retro スキルを起動し、**どこがボトルネックか**を明確にさせる（失敗のバッチ集約・FDCR診断・
提案生成。`harnessdev-checklist.md` → `ecdysis-cross-instance.md` の順で当てるのは harness-retro 側の責務）。
本スキルは診断を再実装せず、旧が特定したボトルネックを起点に次の検証へ進む。

- 成果物は harness-retro が `harness-proposals/<date>-<slug>.md` に diff 形式で出力する。
- 本スキルは、その提案群から**今サイクルで検証する候補を1本選ぶ**（1サイクル1変更理由）。
  選定基準: 横断再発の証拠が最も強く（別タスク数が多い）、副作用が小さく、`失敗帰属=harness` のもの。
  `失敗帰属=model` の提案はハーネス採用の候補にしない（プロンプト微調整に回す）。
- 選んだ候補を台帳の当該サイクルに「候補提案: <path> / 変更理由1行 / 帰属 / 横断 task_id」で記録する。

---

## Step 4: 検証（⑤Jtrain 代理での候補評価）— ここが本スキルの核

論文の受理基準は `Jtrain(candidate) > Jtrain(previous)`（全体スコアが厳密に改善したときだけ採用）。
本環境ではこれを次の手順で代理評価する。**この時点ではまだ harness を書き換えない**（候補の評価）。

1. **人間承認を得て候補を適用**（採用ではなく「試すための適用」）。適用は可逆にする:
   - 対象ファイルを `.bak` 退避してから、承認された diff を反映（harness-retro Step6 と同じ流儀）。
2. **適用後の観測期間**を回す: 以降 N タスク（既定 N=10）の harness-logs を集計し、Step2 と同じ指標で
   `Jtrain(candidate)` を得る。
3. **受理条件**（すべて満たすときだけ「改善」と判定）:
   - 成功率代理が悪化していない（同等以上）
   - 対象だった reason_code の**横断再発が減っている**
   - 効率（turns/tokens）が大きく悪化していない
   - かつ、改善が**その1タスクだけでなく別タスクでも**観測される（ECDYSIS の汎化条件）
4. 判定を「改善 / 悪化 / 判定保留（データ不足）」で台帳に記録する。

---

## Step 5: 採用・棄却・凍結の判断材料提示（⑥）— 決定は人間

Step 4 の判定に基づき、**推奨**を提示する（自動採用・自動棄却はしない）。

- **改善** → 「採用（keep）を推奨。凍結してよいか」と人間に確認する。承認されたら:
  - `.bak` を破棄し、台帳に `採用: <日付> <コミットハッシュ>` と「凍結ハーネス状態」を記録。
  - 凍結＝この harness 状態を次サイクルのベースラインにする（タグ or コミットで固定）。
- **悪化 / 判定保留** → 「棄却（rollback）を推奨」と提示。承認されたら:
  - `.bak` を戻して原状復帰（可逆）。台帳に `棄却: 理由` を記録。
- どちらの場合も、**最終判断は人間**。あなたは根拠（Step4 の指標差分）を添えて推奨するだけ。

---

## Step 6: 台帳の確定と報告（1サイクルで終了）

- 台帳 `harness-evolution-log.md` の当該サイクルを確定させる（ベースライン→候補→検証→決定を1エントリに）。
  これは ECDYSIS の「生ログをフルアクセス可能な形で残す」思想（Meta-Harness arXiv:2603.28052）に沿う。
- **1サイクルで止まる（single-pass）**。自動で次サイクルへは進まない。1回分の「試す→測る→採用/棄却」を
  回し切ったら、必ずここで人間に報告して終了する。これは暴走防止と、1変更ごとに効果を見極めるため。
- 報告内容:
  - 特定したボトルネック（旧 harness-retro の診断） / 試した候補1本 / 検証結果（ビフォー・アフター指標） /
    採用・棄却の推奨と理由 / 現在の凍結ハーネス状態 / まだ残っている再発。
- **続けたい場合**: 残っている再発があり、次の改善を試したいなら、人間が改めて harness-evolve を再実行する
  （もう1サイクル回す）。連続で回すかどうかの判断を人間に残すことで、1変更＝1効果確認の原則を守る。

---

## harness-retro との役割分担（重複しないこと）

| | harness-retro（旧・残す） | harness-evolve（新・本スキル） |
|---|---|---|
| 担当 | **ボトルネックの診断・提案生成**（②③④） | 1サイクル駆動・検証・採用会計（①⑤⑥） |
| 使いどき | 「どこが悪いか診断だけしたい」 | 「改善を1回試して効果まで見届けたい」 |
| 回数 | 1回の診断で完結 | **1サイクル回し切り**（続けるなら人間が再実行） |
| 出力 | `harness-proposals/<date>-<slug>.md` | `harness-proposals/harness-evolution-log.md`（台帳） |
| 承認 | 提案は承認ゲート | 採用・凍結も承認ゲート |
| 関係 | 単体で使える診断器 | retro を内部で**呼ぶ**合成スキル |

診断ロジック（HarnessDev 4落とし穴 / ECDYSIS A〜D）は harness-retro 側に一元化し、
本スキルからは重複実装しない。
