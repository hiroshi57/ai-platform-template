## TL;DR（3行要約）

- **主張**: 論文は、モデルが直接の聞き出しを正しく拒否していても、**無害な出力の統計的性質（数値の選び方・長さ・書式）から in-context secret を復元できる**ことを商用モデル8種で実証した。2桁はほぼ100%、4桁は82%で完全一致。**機密指示を強く書くほど漏れ**、**高性能モデルほど漏れる**。出力フィルタや LLM 審査では検出できない。
- **提案**: ① 秘密をエージェントのコンテキストに入れない原則を明文化（A）② 機密指示は「値を置いて守らせる」でなく「値を置かない」に統一（B）③ 外部テキストを読む Worker と機密を扱う Worker を分離（C）④ 秘密ファイルの Read を settings の deny で機械的に禁止（D・人間が反映）⑤ 記憶・生ログへの秘密混入チェックを retro に追加（E）。
- **効果**: 唯一確実な防御は「コンテキストに無いものは漏れない」。A〜E はいずれも運用ルールと既存の設定機構で実装でき、モデル変更は要らない。

### 承認で決まること（決裁事項）

- ✅ 提案 A〜E を **フェーズ 1（A・B・D）→ 2（C・E）の順で実装してよい**
- ✅ §1 の「漏洩経路の分類」を、レビュー観点の共通語彙として採用する
- ❌ 承認しても本体ファイルへの反映は各提案ごとに**別途レビュー**を経る（一括反映の許可ではない）

**却下・保留する場合**: 提案単位で可（A〜E は相互に独立）。

## 1. 背景: 論文の要点（要約）

### 1.1 何が示されたか

| 発見 | 論文の数値 | 本ハーネスへの含意 |
|---|---|---|
| 直接の聞き出しは全モデルが拒否 | 160回中0%漏洩 | 「拒否できている」ことは安全の証拠にならない |
| 無害な出力から秘密を復元 | 2桁≒100%、4桁82%（Claude Opus 4.6） | コンテキストの秘密は出力分布を歪める |
| 記憶の有無を推定 | 優位度 0.319（文章だけを見る審査役は 0.058） | agent-memory の中身は、文章に出なくても出力に影響する |
| エージェントから SSN を窃取 | 先頭桁 97.1%、残り8桁 76.5%（Claude） | **AGENTS.md / USER.md 型の構成そのもの**が攻撃対象として実験されている |
| 強い機密指示ほど漏れる | Opus: 1行指示 0.054 → 詳細ポリシー 0.643（1桁あたり正解率） | 「絶対に漏らすな」と値を置く書き方は逆効果 |
| 事後学習が進むほど漏れる | OLMo-3: 2.91 bit → 1.37 bit（残存不確実性） | モデルを強くしても改善しない（むしろ悪化） |

### 1.2 仕組み（抑制 suppression）

「X を守れ」と指示されたモデルは、X を出さないよう確率を押しのける。その**歪みそのものが X の手がかり**になる。したがって、守らせる値を指定するほど漏れやすい。逆に、値を特定しない漠然とした指示では、デコーダーが読み取る対象がない。

### 1.3 漏洩経路の分類（本提案の共通語彙）

| 種別 | 内容 | 例 | 出力フィルタで防げるか |
|---|---|---|---|
| **L1 明示漏洩** | 秘密が文章に出る | ログや思考に平文で書く（Claude は SSN 実験の 98.6% で思考に平文を出した） | 一部可 |
| **L2 受動漏洩** | 無害な出力の統計に秘密が乗る | 数値の選び方・長さ・書式の偏り | **不可** |
| **L3 能動漏洩** | インジェクションで符号化させる | 「各桁を ! の個数で表せ」 | **不可**（フィルタは回避すべき制約が1つ増えるだけ） |

## 2. 現行運用の不足点

### 2.1 「秘密をコンテキストに入れない」原則が明文化されていない

- `.claude/rules/` には memory-curation と harness-retro のみで、**秘密の取り扱いルールが無い**。
- グローバル CLAUDE.md のヨシケイ節は「`config/secrets.yaml` はコミット不可」と定めているが、**エージェントが Read してよいか**は定めていない。git 管理の問題と、コンテキスト混入の問題は別物。
- DI-MCP は認証情報をサーバー側で持ち、エージェントにトークンを見せない。これは論文の結論に沿う正しい設計だが、**他案件に揃える方針として書かれていない**。

### 2.2 生ログ逐語保存との組み合わせリスク

CLAUDE.md §7 と memory-curation ルール4は `harness-logs/` の**逐語保存**を定めている（この方針自体は正しい）。しかし `commands.stdout.log` に秘密やクライアントデータが混入すると、**retro で強いエージェントに生ログを読ませるたびに、秘密が再びコンテキストに入る**。逐語保存と秘密排除を両立させる規定が無い。

### 2.3 外部テキストと機密が同じコンテキストに同居しうる

広告レポート、LP の内容、顧客 CSV、Web ページなど、**第三者が書いた文章を読む Worker** が、同じコンテキストに認証情報やクライアントの機密を持つ構成を禁じていない。論文の能動攻撃（L3）は、この同居が前提。

### 2.4 レビュー観点が「出力に秘密が出たか」止まり

4視点レビュー（`/harness-review`）や self_review には、「**そのタスクで秘密をコンテキストに入れる必要があったか**」という観点が無い。L2/L3 は出力を見ても検出できないため、**入力側で止める観点**が必要。

## 3. 提案（A〜E）

### 提案 A: 秘密をコンテキストに入れない原則を rules として明文化

- **変更**: `.claude/rules/secret-isolation.md` を新設（文案は付録 A）。要点:
  1. 認証情報・API キー・アカウント ID・個人情報・クライアントの生データは、**エージェントのコンテキストに入れない**。Read / cat / grep の対象にしない。
  2. 値が必要な処理は、**スクリプトやツールの内部で読み込み、LLM には結果だけを返す**（DI-MCP 方式）。
  3. 秘密ファイルのパスや存在を扱うのはよいが、**中身を表示するコマンドは実行しない**。
- **「禁止事項」への追記**: 上記1を AGENTS.md / CLAUDE.md の「禁止事項」に入れる場合は、§7 の規定により**人間が反映**する。本提案は文案（付録 A）の提示に留める。
- **論文根拠**: §5「コンテキストを共有する限り出力分布は秘密の情報を持つ」（設計上の問題）。

### 提案 B: 機密指示の書き方を「値を置かない」に統一

- **変更**: プロンプト・AGENTS.md・システムプロンプトに**秘密の値を書いたうえで「これを守れ」と指示する構成を禁止**する。値が必要なら提案 A の方式（ツール内部で読み込む）に置き換える。
- **論文根拠**: §4（抑制と漏洩の順位相関 ρ=0.95、強い指示ほど漏れる）。付録 H（別の機密指示で学習したデコーダーがそのまま効く＝指示の言い回しでは守れない）。
- **注意**: 「強く書かなければ安全」ではない。Gemini 3.1 Pro はどの言い回しでも強く漏れた。**値を置かないことだけが確実**。

### 提案 C: 外部テキストを読む Worker と、機密を扱う Worker を分離

- **変更**: Lead がタスクを分解するとき、次の2種類を**同じ Worker に割り当てない**ルールを追加する。
  - (i) 第三者が書いたテキストを読む（Web / LP / 広告レポート / 顧客 CSV / メール本文）
  - (ii) 認証情報・クライアント機密・個人情報をコンテキストに持つ
- 両方が必要な場合は、(ii) をツール側（MCP サーバー / スクリプト）に寄せ、LLM のコンテキストには (i) だけが入るようにする。
- **外部に出る成果物**（クライアント送付 FMT、メール、公開ダッシュボード）を生成する Worker には (ii) を持たせない。
- **論文根拠**: §3.3（インジェクションによる符号化で SSN を窃取、直接要求では0%）。
- **対象外の尊重**: Worker の `disallowedTools: [Agent]`（NG-3）等の既存制約は変更しない。Lead の割り当て方針の追加のみ。

### 提案 D: 秘密ファイルの Read を settings の deny で機械的に禁止（人間が反映）

- **変更案**（案件リポジトリの `.claude/settings.json`。**人間が反映する**）:
  ```diff
   {
     "permissions": {
  +    "deny": [
  +      "Read(**/config/secrets.yaml)",
  +      "Read(**/.env)",
  +      "Read(**/.env.*)",
  +      "Read(**/*.pem)",
  +      "Read(**/*credentials*.json)",
  +      "Bash(cat **/secrets.yaml)",
  +      "Bash(cat **/.env*)"
  +    ],
       "allow": [ ... ]
     }
   }
  ```
- **理由**: rules（提案 A）はエージェントの遵守に依存する。deny は**ツール層で機械的に止まる**ため、ルールを知らないエージェントや弱いモデルにも効く。
- **retro ルールとの整合**: `.claude/rules/harness-retro.md` 提案4「モデル強度より先にツールセットを見直す」と同じ考え方（ツールセットで挙動を形作る）。
- **Bash パターンの補足（反映時）**: Claude Code の Bash ルールは `**` ではなく `*` ワイルドカードで照合するため、反映時は `Bash(cat *secrets.yaml*)`・`Bash(cat *.env*)` とした。[更新: 2026-09-28]
- **既知の限界**: Bash の deny はパターン回避（`head`、`python -c` 等）が可能で完全ではない。**第一防御は提案 A の運用、D は事故防止の安全網**と位置づける。対象パスは案件ごとに人間が確定する（§5 P-1）。

### 提案 E: 記憶・生ログへの秘密混入チェックを retro に追加（advisory）

- **変更**: `harness-retro.sh --check`（または `/harness-release` 前の手動チェック）に、`.claude/agent-memory/` と `.claude/harness-logs/` を対象とした**秘密らしき文字列の検出**を advisory で追加する。
  ```bash
  # 例: キー形式・長い16進/Base64・メールアドレス・ID 形式を検出（誤検知前提の advisory）
  grep -rEn '(sk-[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}|-----BEGIN [A-Z ]*PRIVATE KEY-----|[A-Za-z0-9+/]{40,}={0,2})' \
    .claude/agent-memory .claude/harness-logs 2>/dev/null | head
  ```
- **検出時の扱い**: 自動削除はしない（memory-curation ルール3「削除は明示タスクのときだけ」を尊重）。**人間に通知**し、人間の指示で伏せ字化する。伏せ字化した場合は、何を伏せたかをコミットメッセージに残す（memory-curation の例外規定どおり）。
- **逐語保存との両立**: 生ログは逐語保存を維持する。ただし**保存前に**検証コマンドの出力から既知の秘密値をマスクする（`***` 置換）運用を推奨する。マスクは「要約」ではなく秘密の除去なので、memory-curation ルール4と矛盾しない（§5 P-3 で確定）。
- **論文根拠**: §3.2（記憶は文章に出なくても出力に影響し推定される）。

## 4. 効果測定（承認後）

L2/L3 の漏洩は本ハーネスで直接計測できない（論文と同等の攻撃実験が必要なため）。そこで**入力側の混入量**を代理指標にする。

| 指標 | 測定方法 | 期待方向 |
|---|---|---|
| 秘密ファイルへの Read 試行数 | 提案 D の deny ヒット数（セッションログ） | 減少 → 0 |
| 記憶・生ログ内の秘密らしき文字列 | 提案 E の grep 件数 | 減少 → 0 |
| 外部テキストと機密の同居タスク数 | Lead のタスク分解記録で (i)(ii) 両方を持つ Worker の数 | 0 |
| 値を置いた機密指示の数 | AGENTS.md / プロンプト内の「守れ」＋値の組み合わせを grep | 0 |

## 5. 未解決論点（着手前に個別確定）

- **P-1**: 提案 D の deny 対象パスの確定（案件ごとに秘密ファイルの配置が異なる。ヨシケイは `config/secrets.yaml`、他案件は `.env` 系が中心と想定）。
- **P-2**: 提案 C の「第三者テキスト」の範囲。社内 Slack やクライアントからのメール本文を (i) に含めるか。
- **P-3**: 提案 E の「保存前マスク」が memory-curation ルール4（生ログ逐語保存）の例外として扱えるか。人間の判断で rules に明記する。
- **P-4**: 秘密が本質的にコンテキストに必要なタスク（例: 秘密そのものを扱う実装作業）の扱い。ローカル限定・外部送信なし・ログ非保存を条件に例外とするか。

**確定（2026-09-28・既定案で承認）**:
- P-1: `config/secrets.yaml`・`.env`・`.env.*`・`*.pem`・`*credentials*.json` の5種
- P-2: Web・LP・広告レポート・顧客 CSV・社外からのメール本文。社内 Slack は含めない
- P-3: 保存前マスクを memory-curation ルール4 の例外として認める（秘密の除去であり要約ではない）
- P-4: ローカル限定・外部送信なし・ログ非保存の3条件をすべて満たせば例外

## 付録 A: `.claude/rules/secret-isolation.md` 文案（承認後に反映）

```markdown
# 秘密のコンテキスト隔離ルール

> **適用対象**: 全エージェント（Lead / Worker / Reviewer）
> **起源**: 提案 `harness-proposals/2026-09-25-context-leakage-secret-isolation.md`／根拠 arXiv:2608.19857
> **承認**: （承認日を記入）

## 背景

モデルが秘密の開示を正しく拒否していても、コンテキストにある秘密は無害な出力の統計的性質に乗って漏れうる。
出力フィルタや LLM 審査では検出できない。確実な防御は「コンテキストに入れない」ことだけ。

## ルール（MUST）

1. 認証情報・API キー・アカウント ID・個人情報・クライアントの生データを、Read / cat / grep で表示しない。
2. 値が必要な処理は、スクリプト・ツール・MCP サーバーの内部で読み込み、LLM には結果だけを返す。
3. プロンプトや AGENTS.md に秘密の値を書いて「守れ」と指示しない。値を置かない。
4. 第三者が書いたテキストを読む作業と、機密をコンテキストに持つ作業を、同じ Worker に割り当てない。
5. 外部に出る成果物（送付物・メール・公開画面）を作る Worker に機密を持たせない。
6. `.claude/agent-memory/` と `.claude/harness-logs/` に秘密の値を書かない。混入を見つけたら削除せず人間に報告する。

## セルフチェック（コミット前）

- このタスクで秘密をコンテキストに入れる必要があったか？ → あったなら、ツール側に寄せられないか検討したか。
- 記憶・ログに秘密らしき文字列を書いていないか（提案 E の grep）。
```
