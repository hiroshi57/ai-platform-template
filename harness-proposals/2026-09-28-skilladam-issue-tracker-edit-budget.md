## 2. 現行運用の不足点

### 2.1 retro が「過去に何を試して、どうなったか」を持っていない
retro の起動条件は `escalation_reason` / `reason_code` の再発回数（直近10タスク中3回）である。しかし、ある問題に対して**過去にどの提案を出し、採用されたか、採用後に再発したか**の記録がない。このため次の2つが起こりうる（論文の「方向のぶれ」）。

- 却下済み・効果なしだった案を、別の retro がもう一度出す
- 後の提案が、前に効いていた提案の記述を上書き・打ち消す（例: judge-rubric の「迷ったら低い方」と、別提案の「差し戻しを減らす」方向の改稿が衝突する）

`harness-proposals/*.md` には提案ごとの経緯が書かれているが、問題（issue）単位でまとまっていないため、retro が横断して読むコストが高い。

### 2.2 提案 diff の大きさに基準がない
提案の変更行数は起案者（LLM）の判断に任されている。直近のタスク結果が案件によって良くなったり悪くなったりしている時期でも、大きな改稿が出てくる。論文の実験では、この状況で大きく書き換えると、効いていた制約が壊れて長い課題の性能が落ちた。

### 2.3 人間承認の前に、機械的な前後比較がない
現状、提案の効果は「承認・反映後に §4 で実測」するだけである。反映前に、同じ過去タスクで改善前後を比べる手順がない。このため、承認する人間は diff と論文の根拠だけで判断することになり、**明らかに悪化する提案**を事前に落とせない。

## 3. 提案と diff

### 提案 A: issue 台帳（Evolving Issue Tracker の移植）

- **変更**: `harness-logs/<project-slug>/issue-tracker.json` を新設する。retro は提案を起案する前に必ずこれを読み、起案後に更新する。
- **形式**: 1 issue = `pattern`（何が起きているか）・`status`（open / mitigated / resolved / reopened）・`attempts`（出した提案・採否・採用後の結果）。
- **更新の規則**:
  - 新しい失敗は、既存 issue に当てはまればそこに紐付け、なければ新規作成する
  - 採用済み提案の後に同じ失敗が再発したら `reopened` にし、その attempt の `outcome` に再発を記録する
  - **追記のみ。issue も attempt も削除しない**（`memory-curation.md` ルール3・in-place 更新と整合）
- **retro への効果**: 新しい提案は「その issue で過去に却下・効果なしだった案と同じでないこと」「`resolved` の issue で効いた記述を打ち消さないこと」を台帳で確認してから出す。
- **論文根拠**: §4.1 Moment Estimation（式11〜13）、§5.5 アブレーション、§6.1 Stability。

### 提案 B: 効果のばらつきで絞る編集予算

- **変更**: retro が出す提案 diff の**変更行数（追加＋削除、コードブロック内も含む）**に上限 η を設ける。η は直近の効果のばらつき V から決める。
- **計算**（論文の式16〜18を移植）:
  - Δ_i = 提案 C のゲートで得た、過去タスク i の「新ハーネスのスコア − 旧ハーネスのスコア」。スコアは judge-rubric.v1 の5観点の合計（0〜15）
  - V_t = Δ_i の不偏分散（件数2未満なら 0）
  - V̄_t = β·V̄_{t-1} + (1 − β)·V_t（V̄_0 = 0）
  - η_{t+1} = max(b_min, b_base·(1 − clip(V̄_t / V_max, 0, 1)))
- **暫定パラメータ**（§5 論点 P-2）: b_base = 60 行、b_min = 15 行、V_max = 4.0（Δ の標準偏差 2 点相当）、β = 0.7
- **上限を超える提案**: 自動で却下はしない。提案書の冒頭に `edit-budget-exceeded: <行数>/<η>` を明記し、分割案（先に入れる部分・後回しにする部分）を併記する。人間はそれを見て判断する。
- **C のデータがない間**: η = b_base 固定（単純な diff 上限として働く）。
- **論文根拠**: §4.1 式14〜19、§5.5（編集予算を外すと DP-Avg −6.7pt、DP-Travel で最大の差）。

### 提案 C: 人間承認前の受理ゲート

- **変更**: retro が提案を人間に出す前に、同じ過去タスク k 件を**旧ハーネスと新ハーネスの両方で再実行**し、judge-rubric.v1 で採点して比べる。
- **再実行の対象**: `harness-logs/` の同じ project-slug・同じ mode の過去タスクから k 件（暫定 k = 5）。同じ乱数 seed で選ぶ。`task.json` の `purpose` は `validation` にする（Worker へのプロンプトには含めない — `judge-rubric.md`「検証タスクの書き方」）。
- **ゲート条件**（論文 §5.3 Acceptance Protocol を移植）:
  - **保護観点**: `no-existing-test-regression`・`plans-cc-markers-untouched` は、どのタスクでも 1 点も下がらないこと
  - **改善観点**: 残り3観点のどれかで、k 件平均が +0.4 点以上（暫定）上がること
  - 両方を満たせば `gate: pass`、満たさなければ `gate: fail`
- **gate: fail の扱い**: 提案は破棄せず、`gate: fail` と比較結果を付けて人間に出す（人間が上書きで承認してよい）。同時に提案 A の台帳に attempt として記録する。
- **除外するタスク**: 秘密や第三者テキストをコンテキストに要したタスクは再実行しない（`secret-isolation.md` ルール1・4）。例: クライアントデータを読む CR レポート系。
- **rubric の版**: 前後比較は同じ `rubric_version` の判定同士でのみ行う（`judge-rubric.md` ルール5）。
- **論文根拠**: §4.1 Skill Update（式21〜24）、§5.3、§6.1（採用スキルが初期値を下回らない）。

| 採用後の reopen 率 | 採用済み attempt のうち、後で同じ issue が `reopened` になった割合（導入前は `harness-proposals/*.md` の経緯から遡って算出） | 低下 |
| 提案 diff の平均変更行数 | 提案書の diff 行数を集計 | V̄ が大きい期間に小さくなっている |
| ゲートの予測力 | `gate: pass` と `gate: fail` の提案で、採用後 §4 実測（各提案の効果指標）が改善した割合を比べる | pass 側が有意に高い（差がなければ C は撤回を検討） |
| retro 1回あたりのトークン | 起案〜人間提出までのトークン数（ゲート再実行分を含む） | ゲート分の増加を、再提出・reopen の減少で相殺できているか確認 |

- 効果が確認できない提案は、その時点で止めて撤回してよい（A〜C は独立。B の可変予算は C に依存）。
