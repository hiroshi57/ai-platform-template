# HarnessDev 診断チェックリスト

> 出典: HarnessDev（arXiv:2609.01437, 2026-09）——「LLMは自分のハーネスを作り・育てられるか」を
> 実データで測ったベンチマーク論文。要約すると「作れるが、落とし穴で壊れる」。
> このファイルは harness-retro の Step 3（仮説形成）で毎回上から順に当てるための実務チェックリスト。
> 難しい理論は読まなくてよい。下の5項目を grep で当てるだけでよい。
> （2026-09-28 更新: 原文の再精読で チェック5 を追加、チェック2 に意味的完了ゲートを追記）

## 前提となる考え方（1行ずつ）

- ハーネスは「モデルの重みとは別の、知能が溜まる場所」。だから改善は価値がある。
- 評価は必ず2軸で見る: **Capability（未知タスクで動くか）** と **Efficiency（トークン消費＝コスト）**。
  「うまくいった」だけでなく「何トークン使ったか」も必ず見る。高コスト＝高性能ではない。
- 「ハーネスを書いたモデル」と「その中で動くモデル」は分けて考える（下記チェック3で効く）。

## チェック1: 死にコード／一度も発火していない機能はないか

**論文の知見**: 生成されたハーネスは、宣言はあるのに実行経路に入らない機能が多い
（Code の108部品中18個が一度も動かず、そのすべてが state/memory 関連。checkpointは
26,679回の実行で1回も発火せず。Writing でも587機能中124が死にコード）。「書いた」と「効いている」は別物。

**retroでの当て方**:
- 新しく追加された仕組み（新スクリプト・新オプション・新state保存）が、ログ上で
  実際に呼ばれた形跡があるか grep する。呼ばれていなければ「死にコード候補」。
  ```bash
  # 例: 追加したはずの機能名がログに1度も出ていないか
  grep -rl '<追加した機能名 or 関数名>' .claude/harness-logs/<project-slug>/ || echo "一度も発火していない疑い"
  ```
- 特に state/memory/checkpoint/recovery 系は「定義しただけで使われていない」典型。
  `.claude/state/` や memory への書き込みが実runで発生しているか確認する。

**提案の型**: 「Xを追加する」より先に「既にあるYが死にコードなので消す/繋ぎ込む」を優先。

## チェック2: 「テストを増やす」より「失敗を読んで直す」を提案しているか

**論文の知見**: 自己テストの数と性能の相関はわずか0.13〜0.26（有意ですらない）。
一方「失敗を読んで的を絞って直し、再検証する(revision)」の相関は0.57(p<.0005)。
テストは量ではなく「失敗トレースを読んで直すループ」に価値がある。
また**検証が構文的すぎる**のも典型で、中身の壊れた出力（degenerate submission）を素通しする
（Data 2,325タスク中441が、どのハーネスも検出できない退化出力だった）。

**retroでの当て方**:
- `retries.log` / `commands.stdout.log` を実際に cat し、**具体的な失敗モード**を1つ特定できているか。
  「テストが足りない」で終わる提案はNG。「この失敗がこう起きているから、ここをこう直す」まで書く。
- 良い例（論文）: 「100回中99回が成功報告なのに実際は48回しか通っていない」と気づき、
  早すぎる完了を弾く completion gate を足した → 効いた。
  = **具体的な失敗を露呈させ、修正をエンドツーエンドで検証したとき**に改善が効く。
- **意味的な完了ゲートがあるか**を見る。「成功と report したか」ではなく「実際に合格したか」で
  完了判定しているか。成功報告を鵜呑みにする実装は、早すぎる完了・退化出力を見逃す。

**提案の型**: 「テストを追加する」単独の提案は却下。「観測された失敗 → 原因 → 的を絞った1修正 → 再検証方法」をセットにする。
完了・提出の前に「成功reportではなく実体で合格を確かめる」意味的ゲートを1つ入れる案を優先する。

## チェック3: executorへの過剰適応（co-adaptation）を作り込んでいないか

**論文の知見**: ハードコードされたステップ上限・出力上限・モデル固有の停止ルールは、
実行モデルを替えると壊れる最大要因。ある Opus 製ハーネスは120ステップ上限をハードコードしていて
別モデル(Gemini)で崩壊した（Self-Eval では好成績）。

**retroでの当て方**:
- 提案や既存ハーネスに、**マジックナンバーの上限**（最大ステップ数・最大リトライ・出力文字数上限・
  タイムアウト）が特定モデル前提で埋め込まれていないか確認する。
  ```bash
  grep -rn -E '(max_?steps|max_?turns|max_?tokens|timeout|retry)\s*[:=]\s*[0-9]+' <対象ファイル>
  ```
- あなたは Opus / Codex / 複数mode を使い分けるので、これは実害が出やすい。
  「Opusでは通るがCodexで落ちる」系の失敗がログにあれば、まずここを疑う。

**提案の型**: ハードコード上限は設定化する／モデルに応じて可変にする。特定モデル名を前提にした
停止ルールは避ける。

## チェック4: 見えているスコアだけで改善を採用していないか（過学習）

**論文の知見**: 可視フィードバックのスコア改善は、未知(held-out)タスクでは縮む/消える。
フィードバックと未知スコアが同方向に動くのは53%だけ。同じコミットでもスコアは±4.75点ぶれる。
「ノイズの多いスコアを繰り返し最適化すると、たまたま良かった回を選び、過学習を増幅する」。

**retroでの当て方**:
- 「直近ログで改善したから採用」という論理になっていないか。1〜2件のログだけを根拠にした
  提案は保留（harness-retro本体の「最低2件以上の根拠」ルールと同じ趣旨）。
- 改善提案は**別の場面（別プロジェクト／別タスク種別）でも成り立つか**を一言添える。
  成り立たないなら「この案件固有の対処」と明記して、CLAUDE.md等の全体ルールには昇格させない。

**提案の型**: 全体ルール（CLAUDE.md / AGENTS.md）への昇格は、複数の独立した根拠が揃い、
かつ別文脈でも効くと説明できるときだけ。それ以外は案件ローカルの提案に留める。

## チェック5: 診断を最優先にし、簡易プローブの合格を信じすぎていないか

**論文の知見**: 進化の工程で **失敗診断が最も弱い**。専用のトレース調査は9系統でわずか2回しか呼ばれず、
明示的に中身を見た失敗は全体の0.5〜40.2%に留まった。さらに**小さなプローブは本評価と食い違う**
（あるハーネスは5つのプローブ全通過なのに本セットでは0.584しか取れなかった）。
一方で新規追加コードの多くは実行経路に乗らない（新規169関数/クラスのうち25は呼び出し無し、
31は死にコード経由でしか到達しない）。

**retroでの当て方**:
- 提案の根拠が「軽いチェック／少数の抜き取りで通った」だけになっていないか。
  **実際の失敗トレースを直接 cat して読む**ことを最優先にする（要約・スコアで済ませない。
  Meta-Harness の生ログ主義、ECDYSIS の帰属診断と同じ）。
- 追加しようとしている新コード・新オプションが、**本当に実行経路から呼ばれるか**を1行で説明できるか。
  呼び出し元を示せないなら、それは死にコードを増やす提案。

**提案の型**: 「診断（実トレースの読み込み）→原因特定→1修正→本評価で再検証」の順を守る。
プローブや抜き取りチェックの合格は"仮の手がかり"であって"効いた証拠"ではない、と明記する。

## まとめ（この順で自問する）

1. その新機能、ログ上で本当に発火している？（死にコードでは？）
2. 「テスト追加」で誤魔化さず、具体的な失敗→原因→1修正→再検証になっている？（成功reportでなく実体で合格判定？）
3. モデル固有のハードコード上限を埋め込んでいない？
4. 見えているスコアだけで採用していない？別文脈でも効く？
5. 簡易プローブの合格でなく、実トレースを読んで診断した？新コードは実行経路に乗る？

5つとも通ったものだけを `harness-proposals/` に出す。
