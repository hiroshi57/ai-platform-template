### 1.2 GLM Infra Agent（Dense Feedback）

| 記事の要点 | 本ハーネスの現状 | ギャップ |
|---|---|---|
| 全体の数字（「テスト失敗」「スループット−20%」）だけでは、どの層が悪いのか・次に何を試すかがわからない | Worker の `validation_commands` は1つ以上あればよい | 失敗したときに**どの層**（単体・結合・全体）で落ちたかを残す決まりがない |
| 良いフィードバックは (1) 局所的 (2) 安くすぐ取れる (3) 客観的に検証できる。観測の相関だけで根本原因と決めない | `decision-boundaries.md` ルール1（リトライのたびに新しい情報）、`judge-rubric.md` ルール4（自己申告は証拠にしない） | (3) は既にある。(1)(2) の、**安い層から確かめる**順序がない |
| 最適化の知見を「適用条件・変換方法・制約・検証の証拠」つきのスケルトンとして貯め、確かめたものを戻す | `memory-curation.md` の二層（生ログと蒸留） | 蒸留層（skills）の書式に**適用条件**と**証拠へのリンク**の欄がない（本提案では扱わず §5 P-5 に回す） |
| 人間の役割は、目標と境界を決める・フィードバック環境を作る・危ない変更をレビューする | `decision-boundaries.md` ルール2、本番デプロイ禁止 | **ギャップなし**（今の設計を裏付けるだけ。diff 不要） |

**含意**: 本ハーネスの retro は「生ログを読ませて改善案を出させる」ところまではできている。足りないのは、**出てきた改善案が過学習していないか・ばらつきの範囲を超えているか・費用に見合うか**を確かめる選択側の仕組みと、Worker の失敗を**層で特定する**仕組み。

## 2. 現行運用の不足点

### 2.1 1つの提案書に独立した仮説がいくつも入る
既存の提案書は「提案 A〜D、互いに独立」が通例で、1回の承認で複数を入れる。後で効果が出なかった・悪化したときに、どの提案が原因か切り分けられない（RRSI が編集予算で防いでいる状態）。

### 2.2 「効いた」の基準がばらつきと無関係
SkillAdam 提案 C の閾値 +0.4 点は固定値。同じタスクを同じハーネスで2回走らせたときの差が 0.4 点を超えるなら、この閾値では偶然の差を改善として採ってしまう。

### 2.3 ルールの費用を問わない
`.claude/rules/` は 5 ファイル・提案4〜8まで増えた。すべて Worker / Reviewer のコンテキストに入るが、追加で増えたトークンに見合う効果があったかは誰も測っていない。

### 2.4 案件専用のルールが共通ルールに混ざりうる
retro は特定の案件（例: CR レポート）の失敗ログを読んで改善案を出す。そのとき、その案件の固有名・ファイル名・媒体名をそのまま共通ルールに書き込んでも、止める点検がない。

### 2.5 Worker の失敗の層が残らない
`retries.log` には「最後の失敗コマンド・エラー・修正3行・前回から新しくなったもの」があるが、どの層の検証で落ちたかがない。retro で「全体テストでしか見つからない失敗が多い」のか「単体テストで捕まるのに Worker が見ていない」のかを区別できない。

## 3. 提案と diff

### 提案 A: 1提案1仮説と仮説タグ（RRSI: 編集予算・変更履歴）

- **変更**: retro が出す提案書では、各提案に次の3つを必ず書く。
  - `component`: 変える部分の種類。`rule`（`.claude/rules/*`）・`claude-md`・`skill`・`memory`・`toolset`（allowed/disallowed tools・検索ツール）・`log-schema`（`harness-logs` の項目）のどれか
  - `hypothesis`: 「X を変えると、指標 Y が Z の方向に動く」の形で1文
  - `falsified_if`: 採用後に何が観測されたら仮説が否定されたとみなすか
- **1提案1仮説**: 1つの提案（提案書の中の A・B…）に独立した仮説は1つだけ。1つの提案書に束ねる提案の数は **3つまで**（暫定。§5 P-2）。超える場合は提案書を分ける。
- **否定された仮説を出し直さない**: 採用後に `falsified_if` が観測されたら、その仮説を「否定済み」として記録する（SkillAdam 提案 A が採用されていれば、台帳の attempt に `hypothesis`・`falsified: true` を追記する。採用されていなければ、元の提案書のステータス欄に `[更新: YYYY-MM-DD] 仮説否定: <根拠ログ>` を追記する）。retro は新しい提案の前に否定済みの仮説を読み、同じ仮説を出さない。
- **根拠**: README「Method to code」の edit budget と History（1変更1レコード、component・hypothesis・score・cost・verdict）。

### 提案 B: ノイズ下限・コスト規則・取り置きタスク（RRSI: 選択側）

- **ノイズ下限 δ**: 受理ゲート（SkillAdam 提案 C）の改善閾値を、固定値ではなく `max(0.4, δ)` にする。δ は、**旧ハーネスのまま**同じ k 件を2回走らせたときの、k 件平均スコアの差の絶対値。ゲートを初めて回すときに1回測り、以後は retro 3回ごとに測り直す。
- **コスト規則**: 提案で Worker / Reviewer が毎回読む文書（`.claude/rules/*`・CLAUDE.md・AGENTS.md）が増える場合、提案書に**増える文字数**を書く。増分が 2,000 文字（暫定。§5 P-3）を超える提案は、ゲートの改善が `2 × max(0.4, δ)` 以上のときだけ `gate: pass` とする。文字数が減る提案（剪定・統合）はこの規則の対象外。
- **取り置きタスク**: `harness-logs/<project-slug>/heldout.json` に、retro が**読まない**過去タスクの task_id を置く。新しく保存されたタスクの 5件に1件（task_id の SHA-256 の末尾が 0〜2、約 19%）を自動的に取り置きにする。retro は取り置きのログを読まない。ゲートは「retro が読んだタスク」と「取り置き」の両方で比べ、**取り置き側で下がったら** `gate: fail` とする。
- **前提**: SkillAdam 提案 C（受理ゲート）。ゲートがない間は、コスト規則の「増える文字数を書く」だけを適用する。
- **除外**: 秘密・第三者テキストをコンテキストに要したタスクは、取り置きにも再実行にも使わない（`secret-isolation.md` ルール1・4）。
- **根拠**: README「Noise-adjusted floor, cost rule」「Noise band delta … bootstrap over trials of the base evaluation, or repeated base evaluations」、結果表の evolve / ID held-out / OOD の区別。

### 提案 C: 案件専用ルールの点検（RRSI: 批評役）

- **変更**: retro が提案書を人間に出す前に、共通ルール（`.claude/rules/*`・CLAUDE.md §7・AGENTS.md）への diff に次が入っていないかを点検し、提案書の末尾に結果を書く。
  - `harness-logs/` に現れる **task_id・project-slug** の文字列
  - 特定の案件にしか無いファイル名・パス（例: `data/YYYYMM/`、特定の Excel ファイル名）
  - 特定の媒体名・クライアント名を条件にした分岐（「〜の案件では」）
- **点検の方法**: 正規表現での機械チェック（task_id・slug の一覧と diff の突き合わせ）と、LLM による読み取り（「このルールは、別の案件のタスクでも同じ意味で守れるか」）の2段。
- **見つかった場合**: 自動で却下しない。案件専用なら、その案件の `.claude/rules/` か AGENTS.md に置き場を変える案を併記して人間に出す。
- **根拠**: README「Critic (leakage screen before evaluation) — domain regex denylist plus LLM review, bounded repair」。

### 提案 D: 剪定候補と、行き詰まったときの探索先（RRSI: 剪定・新規性）

- **剪定候補**: retro のたびに、採用から 30 タスク以上たったルールのうち、提案書の `falsified_if` または §4 の効果指標で**効果が確認できない**ものを「外す候補」として列挙する。候補は提案書として人間に出し、**自動では削除しない**（`memory-curation.md` ルール3）。外すと決まった場合も、元の提案書のステータス欄に `[更新: YYYY-MM-DD] 撤回` と理由を追記して経緯を残す。
- **行き詰まりの定義**: 直近3回の retro で、採用された提案が0件、または採用された提案の仮説がすべて否定された場合。
- **行き詰まったときの探索先**: 次の retro では、提案 A の `component` のうち、**これまで採用された提案で一度も使われていない種類**を最低1つ含める（例: これまでが `rule` ばかりなら `toolset` か `skill`）。提案4（ツールセットを先に見直す）の具体化。
- **根拠**: README「Prune set B_t」「Stall flag, untried components, exploration directives」「Novelty nu_t (structural component types never in a winning edit)」。

### 提案 E: Worker の検証を層に分ける（GLM: Dense Feedback）

- **変更**: Worker の `validation_commands` を、可能な範囲で次の層に分ける。
  - `L1 局所`: 変更した関数・ファイルだけのテスト、型チェック、lint
  - `L2 結合`: 変更したモジュールと、その呼び出し元を含むテスト
  - `L3 全体`: ビルド・全テスト・`validate-plugin.sh` などの全体検証
- **順序**: 仮説を確かめるときは、答えが出るいちばん安い層から走らせる。L3 だけで確かめない。ただし完了前には必ず L3 を通す。
- **記録**: `retries.log` の各試行に、失敗した層（`L1` / `L2` / `L3`）を1語残す。層に分けられない案件（テストが1コマンドしか無い）は `L3` と書く。
- **retro での使い方**: 「L3 でしか見つからない失敗」の割合が高い案件は、L1・L2 のテストが足りない、とみなして提案の候補にする。
- **根拠**: 記事「Dense Feedback」の3条件（局所的・安くすぐ取れる・客観的に検証できる）と「局所の検証で誤った変更を早く落とし、全体テストで実際に効くかを確かめる」という役割分担。
